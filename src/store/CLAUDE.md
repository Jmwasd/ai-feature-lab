# store/

`editorStore.ts` 하나뿐인 폴더. 모듈 수준 싱글턴 + `useSyncExternalStore`다.

레이어 전체의 그림은 root의 `ARCHITECTURE.md`를 본다.

## 왜 라이브러리를 쓰지 않는가

React 구독과 **React 밖 구독**이 둘 다 필요하기 때문이다. 캔버스 렌더 루프는 컴포넌트가 아니라 `requestAnimationFrame` 안에서 돌면서 상태 변경을 알아야 한다. 그래서 구독 함수를 두 갈래로 낸다.

```ts
useEditor(selector)   // React 컴포넌트용 (useSyncExternalStore)
subscribeRaw(fn)      // rAF 루프용 — dirty 플래그만 세운다
```

**`useEditor`의 selector는 참조가 안정적인 값을 반환해야 한다.** 원시값이거나 기존 객체 참조여야 하고, 매번 새 객체·배열을 만들면 `useSyncExternalStore`가 무한 루프에 빠진다. 파생값이 필요하면 컴포넌트 안에서 계산한다 — `PropertyPanel`이 `scene`과 `selection`을 각각 구독한 뒤 `selected` 배열을 렌더 중에 만드는 이유다.

`setState`는 **얕은 병합 후 전체 리스너 호출**이다. 선택적 알림이 없으므로, 자주 바뀌는 값을 추가하면 모든 구독자가 깨어난다. 드래그 중 매 프레임 바뀌는 값은 `EditorState`가 아니라 컴포넌트의 ref에 둔다(`CanvasView`의 `Interaction`이 그렇다).

## 히스토리를 잇는 자리

`execute` / `setScene` / `record` 3분기의 뜻과 근거는 `ARCHITECTURE.md`의 불변식 5에 있다. 여기서는 스토어 쪽 조립만 본다.

`canUndo`/`canRedo`는 파생값이라 씬을 갱신할 때마다 `syncHistoryFlags()`로 함께 넣는다 — **빠뜨리면 버튼 활성화가 한 박자 늦는다.** 새 액션이 히스토리를 건드리면 이 호출을 잊지 말 것.

`History`(`core/history.ts`)는 별도 싱글턴이고 씬을 들고 있지 않다. 씬은 인자로 들어가고 결과로 나온다.

## `active`와 `staticEpoch` — 렌더러가 스토어에 의존하는 지점

정적/활성 레이어 분리(`render/layers.ts`)를 위해 스토어가 답해야 하는 질문이 하나 있다. **"방금 바뀐 씬은 정적 레이어를 다시 그려야 하는 변경인가?"**

렌더러는 `scene` 참조만으로 답할 수 없다. 드래그 중에는 매 프레임 새 씬이 만들어지지만 실제로 바뀐 것은 잡고 있는 도형뿐이고, **어떤 종류의 변경인지 아는 것은 스토어뿐이다.** 그래서 히스토리 3분기가 그대로 여기로 이어진다.

| 액션 | `staticEpoch` |
| --- | --- |
| `execute` / `undo` / `redo` / `updateEditingShape` | 올린다 |
| `setScene` — `active`가 비어 있음 | 올린다 (무엇이 바뀌었는지 모른다) |
| `setScene` — `active`가 선언됨 | **올리지 않는다** |
| `record` / 선택·도구·카메라 | 씬을 바꾸지 않으므로 무관 |

`active`는 `CanvasView`가 조작을 시작할 때 넣고 끝낼 때 비우는, **"포인터를 뗄 때까지 바뀔 도형은 이것뿐"이라는 선언**이다. 드래그당 두 번만 바뀌므로 ref가 아니라 스토어에 있어도 된다(아래 "상태를 추가할 때"의 2번 기준을 통과한다).

**예외가 하나뿐이라 기억할 수 있다.** 씬을 바꾸는 새 경로를 만들면 `invalidateStatic()`을 거치게 한다. 빠뜨리면 화면에 잔상이 남고 아무 오류도 나지 않는다 — 개발 빌드에서는 `layers.ts`의 계약 검사가, CI에서는 `npm run bench`의 레이어 정합성 검사가 잡는다.

`setActive`는 **양쪽 다 비어 있으면 아무것도 하지 않는다.** 팬이나 마퀴처럼 도형을 잡지 않은 조작이 끝날 때마다 정적 레이어를 통째로 다시 그리지 않기 위해서다.

## 텍스트 편집 상태

세 필드가 얽혀 있다.

| 필드 | 뜻 |
| --- | --- |
| `editingId` | 편집 중인 도형 id. 씬에 있을 수도, 아직 `draft`일 수도 있다 |
| `editingOriginal` | 편집 시작 시점 스냅샷. 히스토리의 before |
| `draft` | 확정 전 도형. 씬·히스토리·z-order를 더럽히지 않는다 |

`getEditingShape(state)`가 "draft인가 씬인가"를 흡수한다. **편집 중인 도형을 직접 찾지 말고 이 함수를 쓴다.**

`draft`가 씬 밖에 있는 이유는 확정 전 상태가 히스토리와 z-order에 섞이지 않게 하기 위해서다. 도형이 확정되는 시점은 `execute(addShape(...))` 한 곳뿐이어야 한다.

`commitTextEditing`이 왜 스토어에 있는지는 `ARCHITECTURE.md`의 불변식 8에. **여러 번 불려도 안전해야 하고**, 네 갈래를 모두 처리한다.

- draft + 빈 내용 → 도형을 만들지 않고 버린다
- draft + 내용 있음 → `addShape`로 확정하고 선택 도구로
- 기존 도형 + 빈 내용 → `deleteShapes`
- 기존 도형 + 내용 변경 → 입력은 이미 씬에 있으므로 `record`만

이 분기를 고칠 때는 네 경우를 전부 다시 확인한다. 한 갈래만 보고 고치면 나머지에서 도형이 사라지거나 히스토리가 어긋난다.

## 알아둘 동작

- **`setTool`은 선택 도구가 아니면 선택을 지운다.** 도형을 그리기 시작할 때 이전 선택의 핸들이 남아 있으면 안 되기 때문이다.
- **`undo`/`redo`는 선택을 비운다.** 되살아난 도형의 id가 선택에 남아 있으면 핸들이 엉뚱한 곳에 뜬다.
- `state.style`의 `strokeWidth`·`fontSize`만 **화면 기준 px**이다(도형을 만드는 순간 `/ zoom`으로 월드 단위가 된다). 이미 만들어진 도형의 값은 월드 단위라, 속성 패널의 같은 입력 칸이 상황에 따라 다른 단위를 뜻한다 — 화면/월드 경계가 사용자에게 새어 나오는 유일한 지점이다.
- `import.meta.env.DEV`에서 `window.__editor`를 연다. 콘솔에서 `__editor.getState()`로 들여다볼 수 있다.

## 상태를 추가할 때

`EditorState`에 넣기 전에 셋을 확인한다.

1. **정말 전역인가?** 한 컴포넌트만 쓰면 그 컴포넌트의 state나 ref다.
2. **드래그 중 매 프레임 바뀌는가?** 그러면 ref다. 스토어에 넣으면 모든 구독자가 매 프레임 깨어난다.
3. **되돌릴 수 있어야 하는가?** 그러면 씬의 일부이고 `Command`로 표현해야 한다. 카메라·도구·선택은 문서가 아니라 뷰 상태라 히스토리에 남기지 않는다.

## M5에서 여기가 바뀐다

Yjs를 붙이면 `Scene`을 직접 다루던 코드가 전부 영향을 받고, undo는 "내가 한 것만 되돌리기"여야 해서 전역 히스토리 스택을 다시 설계해야 한다. `History`가 씬을 들고 있지 않고 `Command`가 역연산을 아는 형태인 것은 그때를 위한 준비다 — 이 두 성질을 깨지 말 것.
