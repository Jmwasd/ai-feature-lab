# dev/

벤치마크 씬 생성기와 측정 하네스. **개발 빌드에만 실린다.**

**어느 파일을 여나** (레이어 전체의 그림은 root의 `ARCHITECTURE.md`):

| 파일 | 하는 일 |
| --- | --- |
| `seed.ts` | 시드 난수로 재현 가능한 씬 생성 |
| `bench.ts` | 측정 + 정합성 검증 |
| `register.ts` | `window.__bench` 등록 |

CLI(`scripts/bench.mjs`)가 dev 서버를 띄우고 Playwright로 `window.__bench.run(opts)`를 부른다. 표 서식과 exit code는 그쪽에 있다.

이 폴더를 **정적으로 import하면 프로덕션 번들에 딸려 들어간다**(root `CLAUDE.md` 참고). 반대 방향, 즉 `dev/`가 앱 코드를 import하는 것은 정상이다 — 실제와 같은 경로를 재야 하므로 오히려 그래야 한다.

## 재현성이 전부다

`Math.random()`을 쓰면 실행마다 씬이 달라져 **개선인지 운인지 구분할 수 없다.** `seed.ts`는 mulberry32 PRNG에 시드를 받아 같은 옵션이면 언제나 같은 씬을 만든다.

씬 구성에도 근거가 있다. 바꿀 때는 무엇을 재려는지 다시 생각한다.

- **펜 비중 25%를 낮추지 않는다.** 획 하나가 수십 점이라 히트 테스트 비용이 도형 수 × 점 수로 붙는, 이 프로젝트에서 가장 비싼 도형이다. 비중을 낮추면 숫자가 좋아 보이지만 최악이 가려진다.
- **획의 절반에만 필압을 싣는다.** 가변 폭 렌더 경로(조각별 stroke)와 단일 경로를 둘 다 타게 하기 위해서다.
- **회전은 25%에만 준다.** 전부 회전시키면 `getWorldBounds`가 늘 네 모서리를 도는 최악 경로만 재게 되어 실제보다 비관적인 숫자가 나온다.
- **텍스트는 박스를 실제로 재둔다.** 그러지 않으면 폭 0인 도형이 되어 컬링 판정이 진짜 크기로 이뤄지지 않는다.

`--area`는 **밀도**를 바꾼다. 도형 수만 늘리고 면적을 고정하면 결과 개수가 n에 비례해 늘어 공간 인덱스와 전체 훑기가 둘 다 O(n)처럼 보인다. **무엇을 고정하고 무엇을 늘릴지가 측정 설계의 전부다** — 인덱스의 값어치는 한 시점의 숫자가 아니라 기울기에 있다.

## 측정 방법

**앱의 렌더 루프를 타지 않고 `renderScene`을 직접 부른다.** 재려는 것이 실제 프레임 타임이 아니라 **한 프레임을 그리는 데 드는 JS 시간**이기 때문이다. 루프를 거치면 브라우저 스케줄링 흔들림이 신호를 덮는다.

Canvas 2D 호출은 커맨드를 쌓고 즉시 반환하므로 **GPU 래스터화는 이 숫자에 없다.** "도형을 건너뛰면 줄어드는 비용"을 재는 데는 오히려 낫다.

뷰포트(1440×900)와 DPR(1)은 고정이다. 창 크기에 따라 숫자가 달라지면 비교가 무의미해진다.

`measure`는 워밍업 뒤에 잰다(첫 몇 회는 늘 몇 배 느리다). **`measureBatched`는 타이머 해상도 때문에 있다** — `performance.now()`는 지문 채취를 막으려고 일부러 뭉툭하고, 인덱스를 붙인 뒤의 픽은 그 눈금보다 빨라서 한 번씩 재면 전부 `0.000ms`로 나온다. 나노초 단위 연산은 배치를 크게(픽 미스는 2000) 잡는다.

**대조군(`pickTopmostLinear`, `pickInRectLinear`)을 지우지 말 것.** 같은 실행·같은 씬에서 A/B를 재기 위한 것이다. 옛 커밋으로 돌아가 따로 측정하면 기계 상태와 브라우저 버전이 달라 비교가 흐려지고, 도형 수를 바꿔가며 O(n)과 O(log n)이 갈리는 지점을 볼 수도 없다.

**빨라진 대신 새로 생긴 비용을 같은 표에 적는다.** `pickCold`(편집 직후 첫 클릭)가 그것이다 — 인덱스 재구축이 여기 실린다. 질의가 빨라져도 이쪽이 더 비싸면 손해다.

`renderDrag`/`renderDragFull`은 씬을 **미리 8벌 만들어 두고** 잰다. 앱도 매 프레임 `{ ...scene.shapes }`를 하지만 그 얕은 복사가 렌더 시간을 덮으면 레이어 분리의 효과가 보이지 않는다. 8벌인 것은 도형 4만 개에서 맵 복사본이 메모리를 잡아먹지 않게 하려는 것.

두 항목은 **같은 씬·같은 카메라·같은 프레임 배열**을 쓰므로 차이가 "정적 레이어를 다시 그리는가"에서만 나온다. 상태 객체는 매번 새로 만들되 `camera`·`active`·`staticEpoch`는 같은 것을 넘긴다 — 스토어가 드래그 중에 실제로 그렇게 두기 때문이고, 이게 달라지면 측정이 대조군과 같아진다.

## 정합성 검증이 진짜 목적이다

컬링과 공간 인덱스가 왜 조용히 틀리는지는 `ARCHITECTURE.md`의 불변식 4에. 여기서는 **어떻게 잡아내는가**를 본다.

**`verifyIndex`** — 인덱스를 거친 결과와 전체를 훑은 결과를 대조한다. 배율 3종 × 400회 픽 + 200회 마퀴.

**`verifyCulling`** — 버린 도형만 모아 다시 그려서 한 점이라도 칠해지는지 본다. 칠해지면 버리면 안 될 것이 섞여 있었다는 뜻이고, 그 집합을 **반씩 갈라 들어가면**(`bisect`) 범인이 나온다. 도형 하나씩 그려보면 1만 번이지만 이분 탐색이면 몇십 번이다.

여기 두 가지 함정이 박혀 있다. 이 코드를 고칠 때 되살리기 쉬우니 주의한다.

1. **다시 그릴 때 세 배 넓은 화면을 쓴다.** 좁은 화면 그대로 그리면 방금 버린 도형이 `renderScene`에서 또 걸러져 아무것도 안 그려지고, 검사는 언제나 통과한다. 처음에 그렇게 짰다가 **일부러 컬링을 30px 망가뜨려도 통과하는 것을 보고** 알아챘다. 검사가 자기가 검사하려는 코드를 그대로 타고 있었다.
2. **넓은 화면끼리 비교한다.** 좁은 화면과 넓은 화면의 가운데를 맞대면 같은 도형이라도 캔버스 크기에 따라 안티에일리어싱 커버리지가 달라져 0.9%가 어긋난다(최대 30/255). 캔버스 크기를 맞추면 그 잡음이 사라져 **임계값 없이** 정확히 비교할 수 있다.

**`verifyLayers`** — 재는 것은 그리기가 아니라 **캐시 무효화**다. 활성 레이어는 매 프레임 새로 그려지므로 낡을 수가 없고, 조용히 틀리는 쪽은 언제나 정적 레이어다. 그래서 실제 조작이 스토어에 남기는 순서대로 상태를 밀어 넣고(잡기 전 → 드래그 중 → 드래그 중 되돌리기 → 놓은 뒤) **매 단계 정적 레이어의 픽셀을 "그 시점에 남아 있어야 할 도형만 통짜로 그린 화면"과 맞대 본다.**

여기에도 앞의 두 함정에 대응하는 선택이 박혀 있다.

1. **정답은 `withoutShapes`가 만든다.** "활성 집합을 뺀 나머지"라는 정의에서 나온 답이라 검사가 검사하려는 코드(`layers.ts`의 무효화 판단)를 타지 않는다. 실제로 `key.active` 비교를 지우면 '드래그 중'·'놓은 뒤'가, `key.epoch` 비교를 지우면 '드래그 중 되돌리기'가 각각 잡힌다 — **단계마다 겨냥하는 실패가 다르다.**
2. **합성 결과가 아니라 정적 레이어만 본다.** 두 캔버스를 겹쳐 읽으면 투명 캔버스를 한 번 거친 만큼 알파가 두 번 반올림되어 1~2/255가 어긋난다. 같은 크기 캔버스끼리의 불투명 렌더 비교는 정확히 같아야 하므로 **임계값이 필요 없다** — 위의 안티에일리어싱 이야기와 같은 결론이다.

선택도 함께 넣어 둔다(정답 쪽은 비어 있다). 선택 UI가 정적 레이어로 새면 그것도 여기서 걸린다.

**검사를 고쳤으면 일부러 깨뜨려서 잡히는지 확인한다.** 컬링 여유를 임시로 줄이거나 인덱스 질의 범위를 좁혀보면 된다. 확인하지 않으면 검사가 있다는 착각만 남는다.

## 측정 항목을 추가할 때

1. `bench.ts`의 `BenchResult`에 필드 추가 + `runBench`에서 측정
2. `scripts/bench.mjs`의 `ROWS`에 `[키, 라벨, 설명]` 추가 (A/B 대조면 `AB_ROWS`에도)

`ROWS`에 없으면 JSON에는 들어가지만 표에는 안 나온다. 새 정합성 검사는 `bench.mjs`의 `CHECKS` 배열에 추가해야 실패 시 exit 1이 된다.

## 손으로 만져볼 때

```js
__bench.load({ count: 10000 })   // 씬을 실제 에디터에 밀어 넣는다
__bench.run({ count: 40000 })    // 콘솔에서 직접 측정
__editor.getState()              // 상태 들여다보기
```

지금까지의 측정 결과와 거기서 나온 결론은 `ROADMAP.md`의 M3에 있다. 새 숫자를 얻었으면 그쪽 표도 함께 갱신한다 — 이 폴더는 재는 도구일 뿐이고, 재고 나서 무엇을 알게 됐는지는 거기 쌓인다.
