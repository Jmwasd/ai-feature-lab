# render/

씬을 Canvas에 그리는 층. **매 프레임 도는 코드**라 다른 폴더와 비용 감각이 다르다.

**어느 파일을 여나** (레이어 전체의 그림은 root의 `ARCHITECTURE.md`):

- `renderer.ts` — 씬 순회, 카메라 변환, 컬링, 선택 UI
- `layers.ts` — 정적/활성 레이어 분리와 정적 레이어 캐시 무효화
- `textMetrics.ts` — 폰트 측정 (브라우저에 물어봐야 하는 유일한 계산)

## `renderer.ts`는 도형 종류를 모른다

모양 그리기는 전부 `shapes/render.ts`로 넘긴다. 여기가 하는 일은 **순회·변환·선택 UI** 셋뿐이고, 도형이 늘어나도 이 파일은 바뀌지 않는다.

`renderScene`은 `EditorState`를 **인자로 받는다**(간선의 근거는 `ARCHITECTURE.md`의 「레이어와 의존 방향」). 여기서 `getState()`를 부르면 벤치마크와 정합성 검사가 절반 죽는다 — `drawStaticLayer`·`drawActiveLayer`도 마찬가지다.

## 한 프레임의 순서

```
1. enterWorld(opaque)         변환 초기화 후 배경 채우기(정적) 또는 지우기(활성)
2. setTransform(s,0,0,s,...)  s = dpr * zoom. 이후 전부 월드 좌표로 그린다
3. drawGrid                   화면에 걸리는 범위만          ← 정적 레이어만
4. 도형 순회                   editingId 건너뛰기 + isVisible 컬링
5. draft                      포인터 근처라 거를 이유가 없다  ← 활성 레이어만
6. 선택 프레임                 외곽선 → (다중이면) 점선 공통 박스 → 핸들  ← 활성 레이어만
7. marquee                                                  ← 활성 레이어만
```

`renderScene`은 이 일곱을 캔버스 하나에 다 한다. 레이어로 나누면 4번이 갈리고(정적 = 활성 집합을 뺀 나머지, 활성 = 활성 집합만) 나머지는 위 표시대로 한쪽으로 몰린다.

**2번 이후로는 월드 좌표만 쓴다.** 화면 기준 크기가 필요하면 `/ zoom`으로 환산한다 — `HANDLE_SIZE`, `ROTATE_HANDLE_RADIUS`, 선 굵기 `1 / zoom`, 점선 간격까지 전부.

`dpr`은 2번의 `s`에만 들어간다. 백버퍼를 CSS 픽셀이 아니라 디바이스 픽셀로 잡아야(`CanvasView`의 `resize`) 고해상도 화면에서 선명하다.

**활성 레이어는 배경을 칠하지 않고 지운다**(`enterWorld(..., opaque: false)`). 정적 레이어 위에 겹치는 캔버스라, 배경색으로 칠하면 아래 도형이 통째로 가려진다.

## 컬링

```ts
isVisible(shape, view, zoom)   // getWorldBounds + renderPadOf
```

Canvas가 화면 밖 도형을 알아서 잘라내지만 **잘라내기 전에 경로를 다 쌓는 비용은 그대로 든다.** 펜 획 하나가 수십 개의 `quadraticCurveTo`라 이 비용이 지배적이다. 배율 1에서 55.7ms → 2.3ms가 여기서 나왔다.

여유 폭(`renderPadOf`)을 빼먹으면 화면 가장자리에서 도형이 잘린다. 얼마나 삐져나오는지는 도형만 알기 때문에 값과 그 근거는 `shapes/CLAUDE.md`에 있다.

## 레이어 분리 (`layers.ts`)

캔버스 두 장을 겹쳐 놓고 **아래에는 움직이지 않는 도형을, 위에는 조작 중인 것만** 그린다. 도형 하나를 끄는 동안 나머지 수천 개는 픽셀 한 점 바뀌지 않는데도 매 프레임 다시 그려지던 비용이 사라진다. 1만 개에서 드래그 한 프레임이 2.3ms → 0.2ms다.

**같이 사라지는 것이 하나 더 있다.** 도형 수에 비례하던 컬링 순회(`scene.order` 전체 훑기)가 정적 레이어에만 남는다. 드래그 중에는 활성 집합만 돌므로 프레임 비용이 도형 수와 무관해진다. 정적 레이어는 여전히 O(n)이지만 **카메라·씬 구조·활성 집합이 바뀔 때만** 돈다.

### 정적 레이어가 언제 낡는가

판단 근거는 `StaticKey` 하나뿐이다 — `staticEpoch`, `camera`, `active`, `editingId`, 크기, `dpr`. 여기 없는 값이 정적 레이어를 바꾸면 **화면에 옛 픽셀이 남고 아무 오류도 나지 않는다.**

**`scene` 참조를 보지 않고 `staticEpoch`를 보는 것이 핵심이다**(왜 씬 참조로는 답할 수 없는지는 `ARCHITECTURE.md`의 불변식 9). 씬 참조로 판단하면 매 프레임 정적 레이어가 다시 그려져 레이어를 나눈 의미가 통째로 사라진다.

`invalidate()`는 백버퍼가 날아갔을 때 쓴다. `canvas.width = ...`는 **같은 값을 넣어도 내용을 지우므로**, 크기가 그대로인 `ResizeObserver` 호출에서도 불러야 한다.

### 대가 두 가지

- **활성 레이어는 z-order를 무시하고 맨 앞에 뜬다.** 다른 도형 뒤에 있던 것을 끌면 드래그하는 동안만 앞으로 나온다 — 왜 감수하는지는 `ARCHITECTURE.md`의 불변식 9에.
- **함께 끌리는 도형들끼리의 순서는 지킨다.** 활성 집합은 선택한 순서라 그대로 그리면 뒤집힌다. `syncActive`가 집합이 바뀔 때 한 번 z-order로 세운다 — 씬 전체를 훑지만 드래그당 한 번이라 프레임 비용이 아니다.

### 계약

불변식 9(활성 집합이 선언된 동안 바뀌는 도형은 그 집합뿐)를 어기면 잔상이 남는다. 개발 빌드에서는 `checkContract`가 도형 참조를 대조해 콘솔로 알려주고, 프로덕션에서는 O(1)로 믿고 지나간다 — **이 폴더가 계약을 지탱하는 방식은 이 검사 하나뿐이다.**

## 매 프레임 도는 코드의 비용 감각

- **객체를 만들지 않는다.** `isVisible`이 `rectsIntersect`를 쓰지 않고 좌표를 직접 비교하는 이유는 사각형 객체를 만들지 않기 위해서다. 도형마다 한 번씩이면 1만 개 × 60fps = 초당 60만 개다.
- **배열을 새로 만들지 않는다.** `scene.order`를 `filter`·`map`으로 걸러 순회하고 싶어지지만, `for`로 돌면서 건너뛰면 할당이 0이다.
- `drawGrid`는 **화면에 걸리는 범위만** 돈다. 월드 전체를 순회하면 줌아웃 즉시 죽는다. 배율이 낮아지면 `step`을 4배씩 키워 점 개수를 일정하게 유지한다.

## `withRotation`

회전을 적용해 콜백을 돌리고 원래 변환으로 되돌리는 헬퍼다. `rotation === 0`이면 `save`/`restore` 없이 바로 부른다 — 대부분의 도형이 회전 0이라 이 분기가 실제로 값을 한다.

핸들도 각자 이 헬퍼로 기울인다. 상자와 함께 기울어져야 조작 방향과 시각이 일치한다.

## 그리지 않는 것

- `editingId`인 도형 — textarea 오버레이가 대신 보여준다. 겹쳐 그리면 글자가 두 번 보인다.
- `frame.rotatable`이 false일 때의 회전 핸들 — **그리면 집히고, 집히면 되어야 한다.**

무엇을 노출할지는 `getSelectionFrame`이 정한다. 여기서 자체 판단을 넣지 말 것 (`ARCHITECTURE.md`의 불변식 2).

## `textMetrics.ts`

캔버스 컨텍스트 하나를 만들어 돌려쓴다. 공유하므로 **잴 때마다 `ctx.font`를 다시 지정한다** — 다른 도형을 재고 온 뒤라면 폰트가 남아 있다.

줄바꿈 규칙 자체는 `shapes/text.ts`에 순수 함수로 있고 여기는 측정만 제공한다. M5에서 서버가 텍스트 박스 크기를 알아야 하면 폰트 메트릭 테이블로 만든 `MeasureText`를 같은 자리에 끼운다.

`measureTextShape`는 `wrapWidth`가 있으면 폭을 그 값 그대로 두고 줄 수만 센다. 없으면 가장 긴 줄이 폭을 정한다.

## 고친 뒤 확인

그리는 순서나 컬링을 바꿨으면 `npm run bench`. 표에서 볼 것은 다섯이다.

- `renderFit`(전체 보기) — 컬링이 듣지 않는 최악. 여기가 나빠지면 그리기 자체가 비싸진 것이다.
- `render1x` — 컬링이 듣는 일반적인 경우
- `renderDrag`(드래그 중) — 레이어 분리가 겨냥한 상황. A/B 표에 통짜 렌더와 나란히 나온다
- 컬링 정합성 — 버린 도형이 실제로 안 보이는지
- 레이어 정합성 — 정적 레이어가 다시 그려야 할 때를 놓치지 않았는지

레이어 검사는 **정적 레이어만** 통짜 렌더와 맞대 본다. 활성 레이어는 매 프레임 새로 그려지므로 낡을 수가 없고, 조용히 틀리는 쪽은 언제나 캐시가 있는 정적 레이어다. 두 캔버스를 합성해 비교하지 않는 이유는 `dev/CLAUDE.md`에.
