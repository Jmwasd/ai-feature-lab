# jobfit — 계획서

작성일: 2026-08-27 (2026-08-31 개정)
상태: 초안 (구현 시작 전)

## 1. 무엇을 만드는가

채용공고 **링크를 붙여넣으면** Notion에 있는 내 이력서와 대조해 **세 칸으로 갈라주는** 웹 도구.

채용공고를 읽을 때 진짜 알고 싶은 것은 "내가 되냐 안 되냐"가 아니라 **"이력서를 고쳐서 메울 수 있는 칸이 어디냐"** 이다. 그래서 결과를 이렇게 나눈다.

| 칸                    | 정의                                     | 산출물            |
| --------------------- | ---------------------------------------- | ----------------- |
| 갖춘 것 (`covered`)   | 이력서에 근거 불릿이 있다                | 근거 불릿 표시    |
| 안 쓴 것 (`implicit`) | 근거는 있는데 공고의 용어로 안 적혀 있다 | 다시 쓴 문장 제안 |
| 없는 것 (`missing`)   | 근거가 없다                              | 그대로 표시       |

두 번째 칸이 이 프로젝트의 존재 이유다. "GitHub Actions로 배포 자동화"라고 적은 사람이 "CI/CD 구축 경험"을 요구하는 공고 앞에서 자기에게 없다고 판단하는 상황 — 그것을 잡아낸다.

### 세 가지가 전부다

1. 채용공고 **링크**를 던진다
2. **Notion에 등록된 이력서**와 대조한다
3. LLM이 **부족한 부분**을 분석해준다

이 셋에 직접 기여하지 않는 것은 전부 뺐다. 이력서 등록 화면도, 분석 기록 저장도, 누적 갭 순위도 없다.

### 실행 형태

**로컬 전용이다.** `next dev`로 내 기계에서만 돌고, API 키는 `.env.local`에서 읽으며, 배포하지 않는다.

- 이유: 이력서는 개인정보다. 남의 이력서를 받는 순간 보관 책임이 생기고 비용 통제 장치가 필요해진다. 개인 도구로 못박으면 그 문제 전체가 사라진다. 이력서 소스가 내 Notion 계정 하나로 고정된 지금은 더 그렇다.
- 대가: 남에게 보여줄 수 없다. 포트폴리오로서의 가치를 포기한다.

로컬 전용이어도 이력서 원문과 공고 본문은 분석을 위해 OpenAI API로 전송된다. 첫 분석 전에 이 사실과 Notion 읽기 범위를 UI에 짧게 알린다. "로컬"은 서버 DB와 타인 접근이 없다는 뜻이지 외부 모델 API로 데이터가 나가지 않는다는 뜻은 아니다.

### 하지 않을 것

- 분석 결과 저장 (새로고침하면 사라진다)
- 여러 공고에 걸친 누적 갭 집계·순위
- 이력서 편집. Notion에서 직접 고친다
- 자기소개서·커버레터 생성
- 계정·로그인·서버 저장

## 2. 기술 스택

- Next.js 15 (App Router)
- TypeScript strict mode
- Tailwind CSS
- Vitest (단위 테스트)
- `@notionhq/client` (이력서 읽기)
- `@mozilla/readability` + `jsdom` (공고 본문 추출)
- OpenAI API (요구사항 추출 + 매칭 판정 + 문구 제안)

Route Handler라는 서버 계층이 반드시 필요하다. 공고 URL fetch는 브라우저에서 CORS에 막히고, Notion 토큰과 OpenAI 키는 브라우저에 두면 안 된다. 셋 다 서버에서만 돈다.

### 모델

두 호출 모두 **같은 최상위 모델 하나**를 쓰고 모델 ID는 한 곳에 상수로 둔다.

- 이유: 3절이 집계·계산을 전부 코드로 빼냈다. LLM에 남은 작업은 전부 판단이라 싼 모델로 아낄 여지가 없다.

### 저장하지 않는다

이력서는 요청 때마다 Notion에서 읽고, 분석 결과는 화면에만 있다가 사라진다. IndexedDB도 서버 DB도 없다.

- 이유: 저장을 없애면 이력서 버전·판정 캐시·stale 계산·재분석 배너가 통째로 사라진다. 일회성 분석에 그 기계장치는 과하다.
- 대가: 같은 공고를 다시 보려면 다시 호출한다. 새로고침하면 결과가 날아간다.

## 3. 아키텍처 규칙

- **집계·계산을 LLM에 시키지 마라.** 3분할 집계, 블록 ID 실재 검증, 중복 제거는 전부 `src/lib/`의 순수 함수가 한다.
- **LLM은 세 가지만 한다.** (a) 공고 텍스트를 요구사항 목록으로 구조화, (b) 요구사항과 경험의 매칭 판정, (c) 안 쓴 것에 대한 문장 제안.
  - **(b)와 (c)는 한 호출에서 처리한다.** `Verdict`가 이미 판정과 제안을 같은 객체에 담고 있다. 호출을 나누면 제안 호출이 "어느 근거로 쓸지"를 다시 고르게 되어 화면에 보이는 근거와 제안의 출처가 어긋날 수 있다. 병합하면 모델이 방금 고른 근거를 그대로 다시 쓴다.
- **근거가 되는 텍스트는 LLM이 쓰지 않는다.** LLM은 Notion 블록 ID만 반환하고, 텍스트는 코드가 Notion 원문에서 가져온다.
  - 이유: 근거를 지어내는 것이 이 도구에서 가장 치명적인 실패다. 없는 경험이 있다고 나오면 사용자는 그것을 이력서에 적는다. 지어낸 인용을 사후에 걸러내는 것보다 **지어낼 여지를 구조적으로 없애는** 편이 확실하다.
  - 실재하지 않는 블록 ID가 오면 코드가 그 근거를 버린다.
  - 유일한 예외는 (c) 제안 문구다. 그것은 근거가 아니라 제안이며, 아래 근거 확인을 거친다.
- **제안 문구는 근거 안의 사실만 쓴다.** 제안은 새 사실을 더하는 글쓰기가 아니라 선택된 근거를 공고 용어로 표현만 바꾸는 작업이다. 제안에는 사용한 근거 블록 ID를 함께 반환하게 하고, 화면에도 원문 근거를 항상 같이 보여준다. 사용자는 복사 전에 원문과 제안을 대조한다.
  - 코드는 제안이 가리키는 블록 ID가 실재하는지만 검증한다. 한국어 표현을 완벽히 해석해 사실성을 자동 판별하는 별도 검증기는 만들지 않는다.
  - 이유: ID 앵커링은 "그 블록이 실재한다"만 보장한다. "그 블록이 이 요구사항의 근거가 된다"는 여전히 LLM의 주관이다. 이 개인 도구에서는 근거를 바로 보여 주고 사용자가 최종 검토하는 편이 복잡한 자동 필터보다 낫다.
- **LLM의 입력은 비신뢰 데이터다.** 공고 본문과 Notion 원문은 명확히 데이터 구획으로 감싸고, 그 안의 지시문을 따르지 않으며 지정된 JSON 스키마만 반환하도록 프롬프트에 명시한다.
- **LLM 입출력은 strict JSON Schema로 고정한다.** 요구사항은 원자적 항목 하나씩, 판정은 requirement ID 하나당 하나씩 반환하게 한다. 스키마에 맞지 않는 응답은 재시도 또는 "판정 없음"으로 처리한다.
- **API 키와 Notion 토큰은 서버에서만 읽는다.** Route Handler 안에서만 접근하고 `NEXT_PUBLIC_*`에 두지 않는다.
- **프롬프트는 `src/prompts/`에 파일로 둔다.** 코드에 인라인하지 않는다.
- `src/lib/`는 순수 함수만 둔다. React·Next·네트워크·프롬프트를 import하지 않는다.
- 외부 호출(Notion·OpenAI·공고 URL fetch)은 `src/services/`에서만 한다.

### 신원 정보 마스킹은 하지 않는다

로컬 전용이고 내 키로 내 이력서만 보내므로 마스킹의 수혜자가 나 하나다. 배포하게 되면 이 규칙을 처음부터 다시 세워야 한다.

## 4. 데이터 모델

```
ResumeEvidence  근거 한 덩어리
                { blockId, text, company, project }
JobPosting      { sourceUrl?, rawText }
Requirement     { id, text, kind: 'must' | 'nice', requiredMonths? }
Verdict         { requirementId, bucket: covered | implicit | missing,
                  evidenceBlockIds: string[], confidence, suggestion?,
                  suggestionEvidenceBlockIds?: string[] }
```

전부 요청 하나 안에서 살고 죽는다. 영속화하는 것이 없다.

### 근거의 단위는 Notion 블록이다

**안정 ID를 직접 만들지 않는다.** Notion 블록 ID가 이미 영구적이고, 내가 문구를 고쳐도 유지되며, 문서 구조도 이미 계층으로 잡혀 있다. 매칭 판정이 가리키는 것은 이 블록 ID다.

내 이력서의 실제 구조는 이렇다.

```
H2  소프트보울 ( 2024. 02 - 재직중 )              ← 회사 + 기간
  H3  Bidbowl (맞춤형 공공 입찰 정보 구독 플랫폼)   ← 프로젝트
      문단  프로젝트 설명 / 기술 스택 / [ 주요 성과 ]
      불릿  "인프라 & 배포 프로세스 구축"
        코드블록  Docker 멀티 스테이지 빌드 …      ← 알맹이가 여기 있다
```

- **불릿과 그 아래 코드블록을 한 덩어리로 묶는다.** 불릿만 읽으면 "인프라 & 배포 프로세스 구축" 같은 제목뿐이고, 매칭에 필요한 기술명은 전부 코드블록 안에 있다. 코드블록은 내부 줄에 개별 ID가 없으므로(블록 하나에 ID 하나) 앵커는 불릿 블록 ID로 하고 텍스트는 둘을 이어붙인다.
- H2를 회사와 기간으로, H3를 프로젝트로 물고 내려가면서 각 근거에 소속을 붙인다.
- **내 경력 개월 수는 계산하지 않는다.** 이력서에서 확정할 수 있는 것은 해당 회사의 재직 기간뿐인데, 그것은 공고가 묻는 기술 경력 기간이 아니다. 계산해 봐야 요구사항에 대한 답이 아니므로 공고가 요구하는 기간만 표시한다. H2 제목의 `( 2024. 02 - 재직중 )` 구간은 회사명을 뽑을 때 잘라내기만 하고 파싱하지 않는다.
- 노이즈는 코드가 뺀다 — 2단 컬럼 안의 연락처·사진, 빈 블록, 이미지, 텍스트가 극히 짧은 블록.

읽기는 `blocks.children.list` 재귀 순회로 한다. 페이지를 마크다운으로 받는 API는 블록 ID를 주지 않아 앵커링에 쓸 수 없다.

## 5. 페이지 하나

### `/` — 랜딩 겸 분석

저장이 없으므로 라우트를 나눌 이유가 없다. 결과가 같은 화면 아래에 이어서 나온다.

```
[랜딩]  도구 설명 한 줄 + 공고 링크 입력 + [분석]
   ↓  (본문 추출 실패 시) 붙여넣기 textarea가 열린다
[결과]  갖춘 것 / 안 쓴 것 / 없는 것 3칸
```

- 각 항목에 근거 블록 텍스트를 Notion 원문 그대로 표시하고, 소속을 `회사 > 프로젝트`로 함께 붙인다
- `must` / `nice`를 항목에 표시한다. 어느 갭부터 메울지는 이것으로 갈린다
- **기간 조건은 요구치만 배지로 표시한다.** `requiredMonths`가 있는 요구사항에 "요구 경력 3년" 배지를 붙인다. 내 경력 개월 수는 계산하지도 표시하지도 않는다. 3분할 판정은 기술·경험 내용 기준으로 그대로 하고, 배지는 항목에 덧붙는 표시일 뿐 별도 칸을 만들지 않는다.
  - 이유: 이 도구는 고쳐서 메울 칸을 찾는 물건인데, 기간은 이력서를 고쳐도 안 늘어난다. 게다가 이력서에서 확정 가능한 것은 회사 재직 기간뿐이고 그것은 공고가 묻는 기술 경력 기간이 아니다.
- "안 쓴 것"에는 고쳐 쓴 문장 제안 + 복사 버튼
- 판정마다 신뢰도를 함께 보여준다

## 6. 공고 링크를 어떻게 읽는가

**링크가 주 경로고, 막히면 붙여넣기로 떨어진다.**

1. 서버에서 URL을 `fetch`한다 (브라우저 User-Agent 지정)
2. `@mozilla/readability`로 HTML에서 본문을 뽑는다
3. 뽑힌 본문이 임계값보다 짧으면 **실패로 간주**하고 화면에 붙여넣기 textarea를 연다

URL fetch에는 기본 가드레일만 둔다. HTTP/HTTPS만 허용하고 localhost와 사설 IP 주소는 거부하며, 응답 크기 상한·짧은 타임아웃·리다이렉트 횟수 상한을 둔다. 로컬 개인 도구를 위해 별도 네트워크 프록시나 DNS 재검증 계층은 만들지 않는다.

- 이유: 사람인·잡코리아는 봇 차단이 강하고, 원티드 같은 SPA는 정적 HTML에 본문이 아예 없다. 링크만 받는 설계는 한국 채용 사이트 상당수에서 그냥 안 된다. 그렇다고 붙여넣기만 받으면 매번 공고를 긁어 와야 한다.
- 대가: 어느 사이트가 되고 어느 사이트가 안 되는지는 써보기 전에는 모른다. 폴백이 자주 열릴 수 있다.
- 조용히 실패하지 않는다. **"이 사이트는 본문을 읽지 못했습니다. 공고 내용을 복사해 붙여넣어 주세요"** 안내와 함께 폴백 textarea를 연다.

## 7. 호출 구조와 실패 처리

`POST /api/analyze` 하나가 전부를 한다. 입력은 `{ url }` 또는 `{ text }` 중 정확히 하나이며, 길이·형식 제한을 먼저 검증한다. 공고 원문과 근거 목록은 모델 컨텍스트 한도를 넘기지 않도록 각자 상한을 둔다.

```
{ url } 또는 { text }
 1. 공고 본문 확보          URL fetch → 실패면 폴백 신호를 반환하고 끝
 2. 이력서 읽기             Notion 재귀 순회 → ResumeEvidence[]
 3. LLM ①  공고 → Requirement[]  (원자적 문구 / must·nice / 요구 개월 수)
 4. LLM ②  Requirement[] × ResumeEvidence[] → Verdict[]
            블록 ID만 반환. bucket이 implicit이면 suggestion과
            suggestionEvidenceBlockIds도 같은 객체에 채운다
 5. 코드    실재하지 않는 blockId 폐기 · 제안 근거 blockId 존재 검증 · 3분할 집계
 6. 응답    원문 근거와 함께 반환
```

매칭은 **요구사항 전체 × 이력서 전체를 한 번에** 보낸다. 이력서는 한 사람 분량이고 요구사항은 20개 안쪽이라 컨텍스트가 감당한다. 품질 열화가 실제로 관찰되면 그때 배치로 내려간다.

응답이 일부만 오거나 JSON Schema 검증에 실패하면 누락분만 담아 **자동으로 한 번 더** 부른다. 그래도 없으면 화면에 "판정 없음"으로 남긴다.

- 누락을 `missing`으로 간주하지 않는다. LLM이 대답을 안 한 것과 근거가 없는 것을 같게 취급하면 사용자에게 거짓을 만들어 보여주는 쪽이 된다.

| M0   | 스캐폴딩 · 타입 · Notion 이력서 읽기 (블록 ID · 회사/프로젝트 계층 · 코드블록 흡수 · 노이즈 필터)                 | 내 Notion 이력서가 근거 목록으로 나온다                                 |
| M1   | 공고 URL 본문 추출 · 실패 판정 · 붙여넣기 폴백 UI                                                                 | 링크를 넣으면 공고 본문이 뜨고, 막힌 사이트에서는 폴백이 열린다         |
| M2   | 요구사항 추출 · strict schema 검증 · 매칭 판정 + 문장 제안(단일 호출) · 근거·제안 블록 ID 검증 · 부분 응답 재시도 | 지어낸 근거 ID와 형식이 틀린 LLM 응답이 자동으로 걸러진다               |
| M3   | 3분할 화면 · 근거 표시 · 요구 경력 배지 · 제안 표시와 복사 버튼                                                   | 링크 하나를 넣으면 세 칸이 나오고, 안 쓴 것에 근거와 함께 문장이 붙는다 |

M0을 먼저 두는 이유는 이력서 파싱이 나머지 전부의 입력이기 때문이다. 근거 목록이 엉망이면 그 위의 매칭 품질은 볼 필요가 없다.

## 10. 테스트 규율

`src/lib/`의 순수 함수는 **테스트를 먼저 쓰고 구현한다.**

- Notion 블록 트리 → `ResumeEvidence[]` 파싱 (코드블록 흡수, 노이즈 제외)
- 근거 blockId 존재 검증
- 제안 문구의 근거 blockId 존재 검증
- 3분할 집계
- 본문 추출 성공/실패 판정

서비스 경계도 실제 API 없이 mock으로 검증한다.

- Notion 블록 재귀 순회와 페이지네이션
- 공고 URL의 허용/차단 판정, 리다이렉트·타임아웃·응답 크기 제한
- LLM JSON Schema 불일치와 부분 응답 재시도

UI 컴포넌트와 페이지에는 테스트를 요구하지 않는다.

**실제 API를 부르는 골든 케이스는 두지 않는다.** 매 실행마다 돈이 들고 결과가 흔들리는데, 개인 도구 하나에 그 비용과 유지 규율을 감당할 이유가 없다. 매칭 품질은 화면을 보면서 판단한다.

- 대가: 프롬프트를 고쳤을 때 매칭 품질이 나빠진 것을 자동으로 알아챌 방법이 없다.

## 11. 알려진 약점

- 사람인·잡코리아는 봇 차단, 원티드 등 SPA는 정적 HTML에 본문이 없다. **링크가 주 경로지만 상당수 사이트에서 폴백으로 떨어진다**
- Readability는 채용공고 레이아웃에 맞춰 만든 것이 아니다. 사이드바·회사 소개를 본문에 섞거나 요구사항 일부를 버릴 수 있다
- 매칭 판정은 본질적으로 주관적이라 100% 일관될 수 없다. 신뢰도를 함께 보여주는 것으로만 대응한다
- 신뢰도는 모델의 자기평가라 보정된 확률이 아니다. 낮은 신뢰도는 "검토 필요" 신호로만 쓴다
- 이력서에 중복 섹션이 있으면(현재 `Tech Sharing` 아래 두산 AIP가 다시 나온다) 같은 경험이 두 근거로 잡힌다
- 저장하지 않으므로 새로고침하면 결과가 사라지고, 같은 공고를 다시 보려면 다시 호출한다
- 파서가 H2 회사 / H3 프로젝트 / 불릿+코드블록 구조에 의존한다. Notion 페이지를 다른 형태로 개편하면 파서를 고쳐야 한다
- 이력서를 직군별로 나누고 싶어지면 페이지 ID를 하나만 두는 지금 구조를 바꿔야 한다
- 제안의 사실성은 완전히 자동 판별하지 않는다. 제안과 원문 근거를 함께 보이고 최종 사용자가 검토한다
