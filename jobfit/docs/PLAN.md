# jobfit — 계획서

작성일: 2026-08-27
상태: 초안 (구현 시작 전)

## 1. 무엇을 만드는가

채용공고를 붙여넣으면 내 이력서와 대조해 **세 칸으로 갈라주는** 웹 도구.

채용공고를 읽을 때 진짜 알고 싶은 것은 "내가 되냐 안 되냐"가 아니라 **"이력서를 고쳐서 메울 수 있는 칸이 어디냐"** 이다. 그래서 결과를 이렇게 나눈다.

| 칸                    | 정의                                     | 산출물             |
| --------------------- | ---------------------------------------- | ------------------ |
| 갖춘 것 (`covered`)   | 이력서에 근거 불릿이 있다                | 근거 불릿 표시     |
| 안 쓴 것 (`implicit`) | 근거는 있는데 공고의 용어로 안 적혀 있다 | 다시 쓴 문장 제안  |
| 없는 것 (`missing`)   | 근거가 없다                              | 학습 항목으로 누적 |

두 번째 칸이 이 프로젝트의 존재 이유다. "GitHub Actions로 배포 자동화"라고 적은 사람이 "CI/CD 구축 경험"을 요구하는 공고 앞에서 자기에게 없다고 판단하는 상황 — 그것을 잡아낸다.

### 실행 형태

**로컬 전용이다.** `next dev`로 내 기계에서만 돌고, API 키는 `.env.local`에서 읽으며, 배포하지 않는다.

- 이유: 이력서는 개인정보다. 남의 이력서를 받는 순간 보관 책임이 생기고 비용 통제 장치가 필요해진다. 개인 도구로 못박으면 그 문제 전체가 사라진다.
- 대가: 남에게 보여줄 수 없다. 포트폴리오로서의 가치를 포기한다.

### 하지 않을 것

- 공고 URL 크롤링 (사이트마다 구조가 다르고 차단당한다. 유지비가 얻는 것보다 크다)
- 이력서 파일 업로드 (PDF/DOCX 파싱). 텍스트 붙여넣기만 받는다
- 자기소개서·커버레터 생성
- 이력서 여러 개 관리. 단일 이력서 + 버전만 지원한다
- 계정·로그인·서버 저장 (로컬 전용이므로 애초에 성립하지 않는다)

## 2. 기술 스택

- Next.js 15 (App Router)
- TypeScript strict mode
- Tailwind CSS
- Vitest (단위 테스트)
- OpenAI API (요구사항 추출 + 매칭 판정 + 문구 제안)

로컬 전용이면 키를 브라우저에 둬도 실질 위험이 없지만, Next를 유지한다. Route Handler라는 프록시 계층이 있어야 호출 로깅과 골든 케이스를 걸 자리가 생기고, 나중에 마음이 바뀌어 배포할 때 드는 비용이 0이 된다.

### 모델

세 호출 모두 **같은 최상위 모델 하나**를 쓰고 모델 ID는 한 곳에 상수로 둔다.

- 이유: 3절이 카운트·순위·집계를 전부 코드로 빼냈다. LLM에 남은 셋은 전부 판단 작업이라 싼 모델로 아낄 여지가 없다. 그리고 모델을 하나로 고정해야 골든 케이스 일치율이 무엇 때문에 움직였는지 해석된다.

### 저장

이력서와 분석 기록은 **브라우저 IndexedDB에만** 둔다. 서버는 LLM 호출을 중계할 뿐 아무것도 저장하지 않는다.

- 대가: 브라우저 데이터를 지우면 사라진다. JSON export/import를 M1에 넣어 보완한다.

## 3. 아키텍처 규칙

- **금액·순위·집계를 LLM에 시키지 마라.** 카운트, 순위, 중복 제거, 3분할 집계, 근속 개월 수 계산, 사전 매핑은 전부 `src/lib/`의 순수 함수가 한다.
- **LLM은 세 가지만 한다.** (a) 공고 텍스트를 요구사항 목록으로 구조화, (b) 요구사항과 경험의 매칭 판정, (c) 안 쓴 것에 대한 문장 제안.
- **근거가 되는 텍스트는 LLM이 쓰지 않는다.** 코드가 이력서와 공고에 ID를 부여하고, LLM은 그 ID만 반환한다. 텍스트는 코드가 원문에서 잘라낸다.
  - 이유: 근거를 지어내는 것이 이 도구에서 가장 치명적인 실패다. 없는 경험이 있다고 나오면 사용자는 그것을 이력서에 적는다. 지어낸 인용을 사후에 걸러내는 것보다 **지어낼 여지를 구조적으로 없애는** 편이 확실하다.
  - 유일한 예외는 (c) 제안 문구다. 그것은 근거가 아니라 제안이며, 아래 어휘 검증을 거친다.
- **제안 문구는 인용 안의 사실만 쓴다.** 제안에 등장하는 고유명사·기술명이 근거 불릿에 없으면 코드가 그 제안을 폐기한다.
  - 이유: ID 앵커링은 "그 불릿이 실재한다"만 보장한다. "그 불릿이 이 요구사항의 근거가 된다"는 여전히 LLM의 주관이고, 실재하는 불릿에 없는 기술명을 얹은 제안이 가장 위험하다.
- **API 키는 서버에서만 읽는다.** Route Handler 안에서만 접근하고 `NEXT_PUBLIC_*`에 두지 않는다.
- **프롬프트는 `src/prompts/`에 파일로 둔다.** 코드에 인라인하지 않는다. 골든 케이스가 "프롬프트를 고칠 때마다 돌린다"는 규율을 걸 대상이 필요하다.
- `src/lib/`는 순수 함수만 둔다. React·Next·네트워크·프롬프트를 import하지 않는다.
- 외부 API 호출은 `src/services/`에서만 한다.

### 신원 정보 마스킹은 하지 않는다

로컬 전용이고 내 키로 내 이력서만 보내므로, 마스킹의 수혜자가 나 하나다. 한글 이름 정규식은 오탐이 심하고 회사명·제품명을 이름으로 잡으면 매칭 근거가 망가진다.

- **배포하게 되면 이 규칙을 되살려야 한다.** 그 순간 마스킹 부재는 내 이력서 문제가 아니라 남의 이력서 문제가 된다.

## 4. 데이터 모델

```
Resume         단일 이력서. 원문 텍스트 + 버전 + ResumeItem[]
ResumeItem     경험 한 덩어리 (역할 / 시작·종료일 / Bullet[])
Bullet         불릿 한 줄 (안정 ID + 텍스트)
JobPosting     공고 (라벨 + 원문 줄 배열 + Requirement[])
Requirement    요구사항 한 줄 (문구 / 출처 줄 번호 / canonical 키 / must|nice / 요구 개월 수?)
MatchVerdict   requirement → covered | implicit | missing
               + 근거 Bullet ID[] + 신뢰도 + 이력서 버전
               + confirmed(implicit 전용) + override? + stale
SkillDict      canonical 키끼리의 별칭 병합표 (M4)
```

### ID가 두 번 나온다

- **줄 번호**는 분해·추출 단계의 일회성 좌표다. 이력서 분해와 요구사항 추출에서 LLM이 원문의 몇 번째 줄인지를 가리키는 데만 쓰고, 그 뒤 버린다.
- **불릿 안정 ID**는 영구적이다. 승인 시점에 코드가 원문에서 텍스트를 잘라 불릿을 만들면서 부여하고, 사용자가 문구를 고쳐도 유지된다. 매칭 판정이 가리키는 것은 이 ID다.
  - 텍스트 해시를 ID로 쓰지 않는다. 오타 하나를 고친 것이 삭제+추가로 보이면 무관한 판정까지 무효가 된다.
  - 그 대가로 `/resume` 편집은 큰 textarea 재파싱이 아니라 **불릿 배열 UI**여야 한다.

### 판정은 이력서 버전에 매달린 캐시다

공고 원문과 추출된 요구사항만 영구 저장하고, `MatchVerdict`는 `이력서 버전 × 공고`의 캐시로 둔다. 이력서를 고치면 영향받은 판정이 stale이 되고 `/gaps`에 일괄 재분석 배너가 뜬다.

- 이유: 이 도구는 이력서를 고치라고 만든 물건이다. 고쳐서 해결된 항목이 갭 순위에 계속 남아 있으면 피드백 루프가 닫히지 않는다.
- stale 범위는 **불릿 단위**로 계산한다. 오타 하나에 전 기록이 무효가 되면 배너가 상시 켜져 있고 사용자는 그것을 무시하기 시작한다.
  - 참조된 불릿이 수정·삭제되면 → 그 판정만 stale
  - 불릿이 추가되면 → `missing` 판정만 stale (새 근거가 생겼을 수 있다. `covered`·`implicit`은 그대로 유효)

### 사용자의 뒤집기는 판정보다 오래 산다

재분석 후에도 `override`를 다시 씌우고 "내가 고침" 배지를 붙인다. LLM 판정이 override와 같아지면 배지를 뗀다. 해제 버튼을 둔다.

- 이유: 뒤집기가 재분석마다 날아가면 두 번째부터 아무도 뒤집지 않는다. 그러면 5절의 뒤집기 기능이 사실상 죽는다.

### SkillDict는 `/gaps` 집계에서만 쓰인다

ID 앵커링을 도입하면서 매칭 판정은 사전 없이 이뤄진다. 사전이 실제로 쓰이는 곳은 누적 갭의 집계 키 하나뿐이므로 **M4에서 만든다.**

- canonical 키는 요구사항 추출 시점에 LLM이 함께 반환한다. 집계는 순수 함수가 그 키로 group by만 한다. 사전은 키끼리의 별칭 병합에 쓰이고, 병합은 사용자가 승인할 때만 반영한다.
- 집계 직전에 LLM에게 목록을 묶게 하지 않는다. 3절 규칙 위반이고, 공고가 쌓일수록 어제 1위였던 항목이 오늘 세 개로 쪼개진다.

## 5. 페이지 3개

### `/resume` — 이력서 등록

텍스트 붙여넣기 → 코드가 줄 번호를 매김 → LLM이 "N~M번 줄이 하나의 경험, 그중 이 줄들이 불릿"이라는 **구조만** 반환 → 코드가 원문에서 텍스트를 잘라 초안 제시 → 사용자가 고치고 승인 → 안정 ID 부여 후 저장.

자동 분해를 그대로 믿지 않는다. 사람이 확정하는 단계를 반드시 거친다. 다만 분해 단계에서 LLM이 문장을 새로 쓰게 두지는 않는다. 윤색이 승인을 통과하면 이후 모든 근거가 오염되고, 그 오염은 앵커링으로도 못 잡는다. 불릿 자체가 가짜이기 때문이다.

원문은 보관한다. 재분해와 복구에 필요하다.

### `/` — 공고 분석

라벨(회사·직무) 입력 + 공고 붙여넣기 → 요구사항 추출 → 3분할 결과. 분석하면 자동 저장되고 목록에서 삭제할 수 있다.

- 각 항목에 근거 불릿을 함께 표시
- **기간 조건은 3분할에 넣지 않고 배지로 표시한다.** "요구 3년 / 내 경험 1년 7개월". LLM은 요구 기간을 숫자로 추출만 하고 개월 수 계산은 코드가 한다.
  - 이유: 이 도구는 고쳐서 메울 칸을 찾는 물건인데, 기간은 이력서를 고쳐도 안 늘어난다. 3분할에 넣을 이유가 없다.
- "안 쓴 것"에는 고쳐 쓴 문장 제안 + 복사 버튼
- **`implicit`만 확인 대상이다.** 확인해야 `/gaps` 집계에 들어간다. `covered`·`missing`은 바로 집계된다.
  - 이유: 피해가 비대칭이다. `implicit` 오판은 사용자가 없는 경험을 이력서에 적게 만들고, `missing` 오판은 공부 목록이 하나 늘어나는 데 그치며, `covered` 오판은 화면에서 보면 즉시 알아챈다.
- 뒤집기는 확인과 별개 행동이고 세 칸 모두에서 항상 가능하다

### `/gaps` — 누적 갭

지금까지 분석한 공고 전체에서 반복 등장한 항목의 순위.

- `missing`(공부해야 할 것)과 `implicit`(이력서를 고쳐야 할 것)을 **독립된 두 목록**으로 나란히 보여준다
  - 이유: 안 쓴 것이 반복된다면 그것은 공부 신호가 아니라 이력서 수정 신호다. 성격이 다르므로 섞지 않는다.
- 순위는 `must`=2, `nice`=1의 가중 빈도로 매긴다. 가중치는 순수 함수의 상수로 빼둔다
  - 단순 빈도로 매기면 모든 공고가 구색으로 적어두는 우대사항이 필수 자격을 밀어낸다
- 각 항목에서 "어느 공고에서 나왔는지" 역참조
- stale 판정이 있으면 "재분석 필요 N건 — 일괄 실행" 배너

## 6. 구현 순서

| 단계 | 내용                                                                                                                                | 완료 기준                                                           |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| M0   | 스캐폴딩 · 타입 · IndexedDB 래퍼(dump/restore 포함)                                                                                 | 새로고침해도 데이터가 남는다                                        |
| M1   | 줄 번호 기반 이력서 분해 · 불릿 배열 편집 UI · 안정 ID · JSON export/import                                                         | 내 이력서가 경험 단위로 저장되고, 빼냈다 되돌릴 수 있다             |
| M2   | 요구사항 추출(문구·must/nice·요구 개월 수) · 불릿 ID 해석과 검증 · 부분 응답 재시도                                                 | 지어낸 근거 ID가 자동으로 걸러진다                                  |
| M3   | 3분할 매칭 · 결과 화면 · 근거 표시 · 기간 배지 · 확인/뒤집기 · 문장 제안과 어휘 검증                                                | 공고 하나를 넣으면 세 칸이 나오고, 안 쓴 것에 고쳐 쓸 문장이 붙는다 |
| M4   | 공고 줄 앵커링 · 출처 불명 표시 · canonical 키 집계 · 가중 순위 · 두 목록 · 역참조 · SkillDict 병합 승인 · stale 배너와 일괄 재분석 | 공고 5개를 넣으면 순위가 보이고, 이력서를 고치면 갭이 따라 바뀐다   |

M3까지가 "쓸 수 있는 물건"이고, M4가 계속 쓰게 만드는 부분이다.

### 왜 공고 앵커링이 M4인가

가짜 근거는 M3부터 즉시 위험하지만, 가짜 요구사항은 누적되기 전까지는 화면에서 육안으로 걸러진다. M3을 쓰는 동안에는 추출된 요구사항 목록을 사용자가 직접 본다. 피해가 나타나는 곳이 `/gaps`이므로 방어도 거기에 붙인다.

M4에서 추출 프롬프트에 두 가지가 추가된다 — 출처 줄 번호와 canonical 키. 유효한 줄 번호가 없는 요구사항은 코드가 버리되 **"출처 불명 N건"으로 접어서 표시한다.** 조용히 버리면 공고에 실제로 있는데 번호만 잘못 단 항목이 소리 없이 사라지고, 프롬프트가 망가져도 결과가 그냥 짧아 보일 뿐이라 알아챌 방법이 없다.

### M4는 크다

여덟 작업이 완료 기준 하나에 묶여 있다. 쪼개지 않는 대신 M4 안에 하위 체크리스트를 두어 중간 상태가 보이게 한다.

## 7. 호출 구조와 실패 처리

매칭은 **요구사항 전체 × 이력서 전체를 한 번에** 보낸다. 이력서는 한 사람 분량이고 요구사항은 20개 안쪽이라 컨텍스트가 감당한다. 품질 열화가 실제로 관찰되면 그때 배치로 내려간다.

응답이 일부만 오면 누락분만 담아 **자동으로 한 번 더** 부른다. 그래도 없으면 화면에 "판정 없음"으로 남기고 갭 집계에서 제외한다.

- 누락을 `missing`으로 간주하지 않는다. LLM이 대답을 안 한 것과 근거가 없는 것을 같게 취급하면 사용자에게 거짓을 만들어 보여주는 쪽이 된다.

## 8. 테스트 규율

- `src/lib/`의 순수 함수는 **테스트를 먼저 쓰고 구현한다** — 불릿 ID 부여와 stale 계산, ID 해석·검증, 제안 어휘 검증, 3분할 집계, 근속 개월 계산, 가중 순위
- UI 컴포넌트와 페이지에는 테스트를 요구하지 않는다
- **골든 케이스**로 매칭 품질을 고정한다
  - gitignore된 `fixtures/`에 실제 이력서 원문 1개 + 공고 3개를 두고 `npm run golden`으로 **실제 API를 부른다**
  - 기대값은 "요구사항 → 줄 번호 집합 + 판정"으로 적는다. 분해가 줄 번호 기반이라 원문부터 결정적으로 비교되고, fixture에 불릿 ID를 박아둘 필요가 없다
  - 일치율(예: 18/20)을 찍고 첫 통과 결과를 기준선으로 고정한다. 그 아래로 내려가면 실패
  - 녹화된 응답으로 대체하지 않는다. 프롬프트를 고쳐도 응답이 그대로면 아무것도 검증하지 못한다. 녹화가 잡는 파싱·집계 회귀는 이미 순수 함수 TDD가 잡고 있다
  - 자동 강제 장치는 없다. CI가 없고 fixture를 커밋하지 않으므로 이 규율은 규율로만 지켜진다

## 9. 알려진 약점

- 매칭 판정은 본질적으로 주관적이라 100% 일관될 수 없다. 신뢰도를 함께 보여주고 사용자가 뒤집을 수 있게 하는 것으로 대응한다
- 골든 케이스는 실제 API를 부르므로 매번 돈과 시간이 들고 결과가 흔들린다. 일치율 임계값으로만 다룬다
- 이력서를 자주 고치면 재분석 호출이 누적된다. 불릿 단위 stale로 범위를 좁혔지만 0은 아니다
- `/gaps`는 확인된 `implicit`만 집계하므로, 공고를 넣고 확인을 누르지 않으면 갭 뷰가 비어 보인다
- 이력서를 직군별로 나누고 싶어지면 마이그레이션이 필요하다
- 배포하게 되면 신원 마스킹 규칙을 처음부터 다시 세워야 한다
- 줄 번호 기반 분해는 원문 줄바꿈 구조에 의존한다. 줄바꿈 없이 붙여넣은 이력서는 분해 품질이 떨어진다
