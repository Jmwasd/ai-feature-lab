# Architecture Decision Records

## 철학

**한 종목의 최신 공시 맥락을 끊김 없이 보여 준다.** 공개 재무제표·실적일·관련주는 누구나 빠르게 열람하고 관련 종목으로 계속 탐색하게 한다. 비용이 드는 AI 분석은 이 공개 여정 뒤에 인증된 사용자가 명시적으로 요청할 때만 생성한다.

### ADR-001: 초기 범위는 S&P 500 중 50개 종목

**결정**: 초기 지원 목록을 수동으로 검수한 50개 종목으로 제한한다.

**이유**: 500개 전체 적재·검수·분기별 갱신은 초기 제품의 데이터 품질과 사용성을 검증하기 전에 운영 시스템을 크게 만든다. 50개면 검색, 재무 수집, 실적일 확인, 관련 종목 탐색과 결과 검수를 실제 서비스 형태로 검증할 수 있다.

**트레이드오프**: 지원하지 않는 S&P 500 티커가 많다. 지원 종목임을 검색과 상세 페이지에서 분명히 표시하고, 품질 검토 후에만 범위를 늘린다.

### ADR-002: 시세 데이터를 사용하지 않는다

**결정**: 주가·시세·주가 상관계수·주가 차트를 제품에 넣지 않는다.

**이유**: 공시 재무와 사업 관계를 중심으로 하며, 가격 데이터의 라이선스와 재배포 검토를 추가하지 않는다.

**트레이드오프**: 사용자가 기대할 수 있는 주가 차트가 없다. 이 제품은 가격 화면이 아니라 공시·사업 관계 탐색 화면으로 한정한다.

### ADR-003: 관련주는 후보 생성 후 후보 쌍의 매출 성장률만 검토한다

**결정**: 수동 LLM 배치가 사업 관계 후보를 만들고, 지원 티커인지 확인한 뒤 그 후보 쌍에 대해서만 분기 매출 성장률 상관계수와 표본 수를 계산한다. 결과는 최대 5개다.

**이유**: 모든 지원 종목쌍을 저장·운영할 이유가 없다. 사용자가 보는 후보의 숫자만 계산하면 되고, 후보 품질을 검수할 수 있다.

**트레이드오프**: 상관계수는 사업 관계의 인과를 증명하지 않는다. 화면과 AI 리포트에서 “검증” 또는 투자 판단 표현을 쓰지 않고, 동행 정도와 표본 수로만 설명한다.

### ADR-004: 공개 종목 데이터는 버전이 있는 정적 스냅샷으로 배포한다

**결정**: `src/data/market-data.json`을 검색·상세 페이지의 읽기 모델로 사용한다. 갱신 작업은 새 공시와 실적일 변경을 수집·검증한 뒤 **변경된 종목의** `dataVersion`을 올리고, 성공한 결과만 정적으로 배포한다. 한 종목의 갱신이 다른 종목의 기준일이나 리포트 캐시를 무효화하지 않는다. 미지원 티커와 결손 데이터도 이 읽기 모델의 명시적 상태로 처리한다.

**이유**: 검색과 공개 상세 요청에 외부 API 호출을 넣지 않아도 빠르고 일관되게 수치를 보여 줄 수 있다. 하나의 `MarketSnapshot` 버전을 재무제표·실적일·관련주·AI 리포트가 공유하면 서로 다른 분기의 데이터가 섞이지 않는다.

**트레이드오프**: 데이터는 실시간이 아니며 갱신 작업과 배포가 필요하다. 부분 실패 시 마지막 정상 스냅샷을 유지하고, 화면에 기준일·출처·상태를 표시한다.

### ADR-005: 재무제표는 확정·잠정·결손 상태를 구분한다

**결정**: 10-Q·10-K XBRL 값은 `확정`, 8-K Item 2.02 보도자료에서 검증 가능한 분기 매출은 `잠정`, 나머지 결손은 `데이터 없음`으로 저장·표시한다. 기본 요약은 매출, 매출 YoY 성장률, 영업현금흐름이며 확장 표는 명시적으로 매핑한 표준 XBRL 항목만 사용한다.

**이유**: 실적 발표 직후의 정보 유용성과 정식 재무제표의 신뢰성을 함께 제공하되, 서로 다른 공시 성격을 혼동시키지 않는다.

**트레이드오프**: 기업별 XBRL 태그와 기간이 달라 일부 필드가 비어 보일 수 있다. 대체 태그·0·대시로 추정해 채우지 않는다.

### ADR-006: 다음 실적 발표일은 독립된 일정 데이터로 관리한다

**결정**: 다음 발표일은 기업 IR 공지를 우선 사용하고, 계약한 일정 제공자의 날짜는 `예상`으로 구분한다. 둘 다 없거나 충돌하면 `발표일 미정`으로 표시한다.

**이유**: SEC EDGAR는 발생한 공시를 제공하므로 미래 발표일을 완전하게 제공할 수 없다. 재무 공시 데이터와 실적 일정 데이터를 하나의 출처처럼 취급하지 않는다.

**트레이드오프**: 일정 제공자 계약 또는 IR 수집 운영이 추가되며, 발표일 변경·누락을 주기적으로 재확인해야 한다.

### ADR-007: Google OAuth는 AI 리포트에만 적용한다

**결정**: 재무제표·실적일·관련주는 공개하고, AI 분석 리포트의 생성·본문 조회만 Google OAuth 세션으로 보호한다. 비로그인 사용자가 명확히 `리포트 생성`을 선택하면, 해당 종목·스냅샷·생성 의도를 검증 가능한 OAuth 상태에 보존하고 로그인 후 원래 종목의 리포트 패널로 돌아온다. 단순한 URL 접근이나 상세 재방문은 새 리포트를 생성하지 않는다.

**이유**: 첫 방문자가 계정 장벽 없이 핵심 정보를 판단하게 하면서도, 로그인 중 종목 맥락을 잃지 않고 의도한 리포트 요청을 한 번에 완료하게 한다. 동시에 링크만으로 비용이 발생하는 일과 AI 호출 남용을 막는다.

**트레이드오프**: Google Cloud OAuth 설정, 개인정보 처리 고지, 세션 운영과 짧은 수명의 생성 의도 관리가 필요하다. 로그인 이전에는 리포트 본문이나 캐시된 첫 문단도 반환하지 않는다.

### ADR-008: AI 리포트는 스냅샷 버전 단위로 캐시·제한한다

**결정**: AI 리포트는 OpenAI Responses API의 `gpt-5.6-terra`로 생성한다. 리포트 키는 `ticker + dataVersion + promptVersion`으로 구성하며, 초기 버전에서는 외부 도구를 사용하지 않고 공개 화면과 같은 `market-data.json`의 확정 재무 데이터만 서버에서 입력으로 사용한다. 인증을 확인한 후에만 캐시를 조회한다. 새 생성은 로그인된 사용자의 명시적 요청 또는 OAuth 콜백이 재개한 검증된 생성 의도에서만 시작하며, 사용자별·전역 호출 한도를 원자적으로 예약하고 실패 시 취소한다.

**이유**: Terra는 성능과 비용의 균형을 목표로 하는 모델이며, 화면과 같은 검증 스냅샷만 분석하게 하면 외부 정보나 별도 저장소의 갱신 시점 때문에 공시 기준일이 흐려지는 일을 막을 수 있다. 동일한 데이터의 반복 비용을 줄이고, 새 공시가 나온 뒤 이전 분석이 최신 결과처럼 보이는 문제도 막는다.

**트레이드오프**: 정적 JSON 외에 인증 세션·캐시·사용량을 위한 서버 저장소와 보호된 API가 필요하다.

### ADR-009: 법적·호스팅 판단을 단정하지 않는다

**결정**: 매수·매도·목표가·수익 보장을 제공하지 않고, 공시 기준일과 면책 고지를 둔다. 무료 운영, 면책, 특정 호스팅 플랜만으로 규제·데이터 라이선스·이용 조건의 위험이 사라진다고 문서화하지 않는다.

**이유**: AI 리포트와 실적 일정은 외부 데이터·자동화·비용을 추가한다. 사업화·개별 상담·유료화 시의 판단은 서비스 형태와 당시 규정에 따라 별도로 필요하다.

**트레이드오프**: 배포 전 외부 조건을 점검해야 한다. 법적 판단이 필요한 변경은 별도로 검토한다.
