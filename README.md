# lab-ai — 협업 캔버스 에디터

Canvas 2D 기반 화이트보드 에디터. 도형을 그리고, 옮기고, 되돌리고, 최종적으로는 여러 명이 동시에 편집한다.

라이브러리로 덮지 않고 렌더링·좌표계·히스토리·협업을 직접 구현하는 것이 목적이다.

## 실행

```bash
npm install
npm run dev      # http://localhost:5173
npm run build    # 타입체크 + 프로덕션 빌드
npm run lint
```

## 벤치마크

```bash
npm run bench                      # 도형 1만 개
npm run bench -- --count 40000     # 도형 수 바꾸기
npm run bench -- --area 12000      # 흩뿌릴 월드 크기 (밀도가 달라진다)
npm run bench -- --save base       # 결과를 .bench/base.json에 저장
npm run bench -- --diff base       # 저장해둔 결과와 비교
```

씬은 시드 난수로 만들어 실행마다 똑같다. 그래야 최적화 전후 차이가 **개선인지 운인지** 구분된다. 매 실행 끝에 정합성을 셋 확인한다 — 공간 인덱스의 결과를 전체 훑기와 대조하고, 컬링이 버린 도형을 다시 그려보고, 정적 레이어를 통짜 렌더와 픽셀 단위로 맞대 본다. **빨라진 대가로 조용히 틀리지 않았는지**를 보는 것이고, 어긋나면 exit code 1이다.

측정 결과와 거기서 나온 결론은 [ROADMAP.md](./ROADMAP.md)의 M3에 있다.

## 설계 노트

### `core/`는 브라우저를 모른다

`camera`, `geometry`, `transform`, `commands`, `history`는 전부 순수 TypeScript다. `window`도 `document`도 Canvas도 참조하지 않는다.

의도적인 규율이다. 실시간 협업 단계에 가면 **서버가 같은 히트 테스트와 좌표 계산을 재사용해야 한다.** 편집 요청을 검증하거나 스냅샷을 만들 때 클라이언트와 다른 로직을 쓰면 결과가 갈린다. 지금 이 경계를 지켜두면 그때 파일을 그대로 가져다 쓸 수 있다.

브라우저 의존은 `render/`와 `ui/`에만 둔다. 도형별 모듈(`shapes/`)이 생기면 그 안의 `draw`도 예외로 허용하되, 순수 함수와 섞지 않고 별도 export로 분리한다.

### 도형 추가는 파일 하나로 끝나야 한다

도형 종류별 로직은 `shapes/`에 모여 있고, 렌더러와 히트 테스트는 어떤 도형이 있는지 모른다. 도형을 추가할 때 기존 파일을 고치는 대신 파일 하나를 새로 쓰고 레지스트리에 등록한다.

레지스트리가 두 파일로 나뉜 이유는 `registry.ts`(히트 테스트)를 순수하게 유지하기 위해서다. Canvas에 의존하는 `render.ts`와 섞으면 서버가 판정 로직만 골라 쓸 수 없다.

### 펜의 점은 바운딩 박스 기준으로 정규화한다

`PathShape.points`는 절대 좌표가 아니라 **0~1로 정규화된 값**이다. 절대 좌표로 두면 리사이즈할 때마다 모든 점을 다시 계산해야 하고, `x/y/width/height`와 정보가 중복된다.

정규화해두면 바운딩 박스만 바꿔도 점들이 따라온다. 그래서 **펜을 추가하면서 리사이즈·회전 코드를 한 줄도 고치지 않았다.** 모든 도형이 같은 바운딩 박스 모델을 공유한 덕분에 레지스트리가 맡는 일은 히트 테스트와 그리기 둘뿐이다.

대신 판정과 렌더는 정규화 좌표를 월드로 펼친 뒤에 한다. 정규화 공간에서 거리를 재면 바운딩 박스의 종횡비만큼 왜곡되기 때문이다.

**선과 화살표도 같은 방법으로 흡수했다.** 선은 양 끝점이 실체이고 박스는 파생물이라 이 모델에 가장 안 맞는 도형이지만, 두 끝점을 박스 기준으로 정규화하면 어느 대각선인지가 좌표에 그대로 남는다. 덕분에 선을 추가하면서도 리사이즈·회전 코드는 건드리지 않았다.

대가는 있다. 수평선·수직선은 한 축의 폭이 0인 퇴화 박스가 되고, 핸들이 겹친다. 끝점을 직접 집어 옮기고 싶어지는 순간 — 핸들 구성이 도형마다 달라지는 순간 — 이 모델은 한계에 부딪힌다.

### 필압은 점에 실어 보낸다

`PathShape.points`의 각 점이 `pressure`를 함께 들고 있다. 별도 배열로 두지 않은 이유는 단순화 때문이다. RDP는 점을 솎아내므로 배열이 둘이면 인덱스를 맞춰가며 같이 솎아야 한다.

점에 실어두면 그럴 필요가 없다. `simplifyPath`는 점을 새로 만들지 않고 **원본 원소를 그대로 통과시키므로**, 제네릭으로 바꾼 것 말고는 고칠 곳이 없었다. 필압은 저절로 따라온다.

**가변 폭 획은 경로 하나로 그릴 수 없다.** `lineWidth`는 경로마다 하나뿐이다. 그래서 점마다 짧은 곡선 조각으로 끊어 각자의 굵기로 긋고, 조각 사이 이음매는 둥근 캡이 메운다. 필압이 없는 획(마우스)은 예전처럼 경로 하나로 긋는다 — 훨씬 싸기 때문이다.

포인터 이벤트는 화면 갱신 주기에 맞춰 합쳐져 들어온다. 빠르게 그으면 그 사이 위치가 통째로 버려져 획이 각지므로, `getCoalescedEvents()`로 합쳐지기 전의 원본을 꺼내 전부 반영한다.

### 히트 판정의 여유 폭은 화면 기준이다

얇은 선을 집으려면 실제 굵기보다 넉넉한 여유가 필요하다. 이 여유를 월드 단위로 고정하면 축소했을 때 획이 화면상 실오라기가 되어 집을 수 없다.

그래서 `hitTest`가 `zoom`을 받는다. **판정이 카메라를 알아야 하는 첫 사례다.** 도형은 여전히 월드 좌표로만 생각하고, 화면 기준 값(`6px`)을 `/ zoom`으로 월드에 환산해 쓴다 — 핸들 크기와 같은 방식이다.

### 텍스트만 크기를 스스로 정하지 못한다

다른 도형은 사용자가 크기를 정하지만 텍스트는 폰트가 정한다. 그래서 텍스트는 이 프로젝트에서 **유일하게 브라우저에 물어봐야 크기를 알 수 있는 도형**이다(`render/textMetrics.ts`).

이 때문에 레지스트리에 `adjustAfterResize`가 생겼다. 지금까지 모든 도형은 바운딩 박스만 바꾸면 리사이즈가 끝났지만, 텍스트는 박스를 키우면 글자도 함께 커져야 한다. **도형별 리사이즈가 처음으로 갈라진 지점이다.**

글꼴 크기는 축이 하나뿐이라 비균등 스케일을 표현할 수 없다. 그래서 더 많이 끌린 축을 골라 균등 스케일한다.

**핸들에 따라 리사이즈의 의미가 갈린다.** 좌우 핸들은 글자 크기가 아니라 줄바꿈 폭(`wrapWidth`)을 바꾸고, 코너·상하 핸들이 글꼴을 키운다. 폭만 끌었는데 글꼴까지 커지면 고정 폭 문단을 만들 수 없기 때문이다. 그래서 `adjustAfterResize`는 "어느 핸들을 끌었는지"를 함께 받는다.

### 줄바꿈 규칙은 순수하게, 측정만 주입한다

줄바꿈은 폭을 재야 하니 브라우저가 필요해 보이지만, 필요한 것은 **글자 폭을 재는 함수 하나**뿐이다. 그래서 규칙은 `shapes/text.ts`에 순수 함수로 두고 `ctx.measureText`는 밖에서 넣는다(`render/textMetrics.ts`).

서버가 같은 줄바꿈을 재현해야 할 때(M5) 폰트 메트릭 테이블로 만든 함수를 같은 자리에 끼워 넣으면 된다. 같은 이유로 리사이즈 뒤처리도 측정 함수를 주입받아 `shapes/registry.ts`를 순수하게 유지한다.

규칙 자체는 단어 단위로 채우다가, **단어 하나가 통째로 폭을 넘으면 글자 단위로 끊는 것**이다. 후자가 없으면 띄어쓰기 없이 이어지는 한국어·일본어 문장이 한 줄로 삐져나간다.

편집 중에는 브라우저의 줄바꿈에 맡긴다(`white-space: pre-wrap`). 캔버스 쪽 규칙과 완전히 같지는 않아 경계에 걸친 한 단어가 다르게 접힐 수 있지만, textarea 안에서 캐럿 이동과 선택을 직접 구현하는 것보다 낫다.

### 캔버스는 `mousedown` 기본 동작을 막는다

`mousedown`의 기본 동작은 포커스를 옮기는 것이다. 텍스트 도구로 캔버스를 클릭하면 `pointerdown`에서 textarea가 마운트되고 포커스를 받는데, **곧이어 도착하는 `mousedown`이 포커스를 다시 빼앗아 간다.** 그 blur가 편집 확정 로직을 호출하고, 아직 아무것도 입력하지 않았으니 방금 만든 도형이 버려진다. 결과는 "텍스트 입력이 아예 안 되는" 증상이다.

그래서 캔버스에서 `mousedown`의 기본 동작을 막는다. 캔버스 자체는 포커스를 받을 일이 없고 키 입력은 `window`에서 듣기 때문에 잃는 것이 없다.

**대신 대가가 하나 있다.** 캔버스를 클릭해도 blur가 발생하지 않으므로, 편집 중에 다른 곳을 클릭해 끝내는 경로가 저절로 동작하지 않는다. `onPointerDown` 첫머리에서 명시적으로 확정한다. 이것이 확정 로직이 편집기 컴포넌트가 아니라 스토어(`commitTextEditing`)에 있는 이유다 — 두 경로가 같은 처리를 공유해야 한다.

### 편집기는 캔버스 위에 겹친 진짜 textarea다

Canvas에는 텍스트 편집기가 없다. IME, 커서, 선택 영역, 클립보드를 직접 구현하는 건 현실적이지 않으므로 **실제 `textarea`를 캔버스 위에 절대 위치로 띄우고** 카메라 변환에 맞춰 위치·크기·회전을 따라가게 한다.

편집 중인 도형은 렌더러가 건너뛴다. 그러지 않으면 캔버스에 그려진 글자와 textarea의 글자가 겹쳐 두 번 보인다.

편집 중에는 캔버스 단축키를 전부 비활성화한다. 그러지 않으면 `v`를 입력하는 순간 도구가 바뀌고 `Backspace`가 도형을 지운다. 속성 패널의 입력 칸도 같은 이유로 걸러낸다.

### IME 조합 중의 `Enter`와 `Escape`는 IME의 것이다

한글 입력에서 `Enter`는 조합 확정, `Escape`는 조합 취소를 뜻한다. 이걸 확인하지 않고 편집 종료로 처리하면 **확정하려던 글자가 사라지거나, 한 글자만 되돌리려던 `Escape`가 편집 전체를 닫는다.**

그래서 `compositionstart`/`compositionend`로 조합 상태를 직접 들고, 조합 중에는 종료 키를 무시한다(`KeyboardEvent.isComposing`도 함께 확인한다 — 조합을 끝내는 키에서 브라우저마다 값이 갈린다).

`compositionend`에서 박스 크기를 한 번 더 잰다. 브라우저에 따라 조합이 확정된 뒤 `change`가 오지 않아, 이게 없으면 마지막 글자만큼 박스가 모자란다.

### 속성 패널은 미리보기와 확정을 나눈다

React의 `onChange`는 DOM의 `input` 이벤트다. 색상 피커를 끄는 내내, 숫자를 한 글자씩 고치는 내내 들어온다. 그대로 히스토리에 쌓으면 **되돌리기 한 번이 색 한 단계씩 되감긴다.**

그래서 드래그와 같은 규칙을 쓴다 — `input`은 씬에 바로 반영하고(`setScene`), 조작이 끝나는 시점인 DOM `change`에서 커맨드 하나를 히스토리에만 기록한다(`record`). `change`는 React가 그대로 노출하지 않아 직접 붙였다.

**패널이 무엇을 보여줄지는 도형 모듈이 정한다.** 각 모듈이 `styleFields`로 자기가 지원하는 속성을 선언하고, 패널은 선택된 도형들의 합집합을 그린다. 펜과 선은 `strokeWidth`, 텍스트는 `fontSize`·`fontFamily`·`align`, 사각형과 타원은 채움과 선 색이다. 도형을 추가해도 패널 코드는 바뀌지 않는다.

선택이 없을 때는 **앞으로 만들 도형의 기본 스타일**을 편집한다. 이때의 굵기와 글자 크기는 화면 기준 px이고, 도형을 만드는 순간 `/ zoom`으로 월드 단위가 된다. 어느 배율에서 그리든 화면에 보이는 크기가 같아야 하기 때문이다. 이미 만들어진 도형의 값은 월드 단위라, 같은 입력 칸이 상황에 따라 다른 단위를 뜻한다 — 이 프로젝트에서 화면/월드 경계가 사용자에게 새어 나오는 유일한 지점이다.

### 렌더링은 React 밖에서 한다

`CanvasView`는 마운트 시 한 번 `requestAnimationFrame` 루프를 열고, 스토어 변경을 구독해 dirty 플래그만 세운다. 도형을 드래그하는 동안 React 리렌더는 **한 번도 일어나지 않는다.** 도형이 수천 개로 늘어나도 리렌더 비용이 붙지 않게 하려는 의도다.

React가 담당하는 것은 툴바 같은 UI 셸뿐이다.

### 좌표계는 두 개다

- **스크린 좌표** — 캔버스 좌상단 기준 CSS 픽셀. 포인터 이벤트가 주는 값.
- **월드 좌표** — 무한 캔버스 상의 절대 위치. 모든 도형이 저장되는 좌표계.

`camera`는 뷰포트 좌상단이 가리키는 월드 좌표와 배율을 들고 있다. 도형을 그릴 때는 변환 행렬을 한 번 걸어두고, 이후 전부 월드 좌표로 그린다. 선 굵기만 `1 / zoom`으로 보정해 화면상 두께를 일정하게 유지한다.

### 히스토리는 스냅샷이 아니라 역연산으로

씬 전체를 스냅샷으로 쌓으면 구현은 쉽지만 메모리가 선형으로 불어난다. 대신 각 `Command`가 `apply`와 `invert`를 함께 들고 변경분만 기록한다.

이 구조는 나중에 협업으로 넘어갈 때 그대로 **네트워크로 전송할 "편집 의도" 단위**가 된다.

### 드래그 중에는 히스토리를 건드리지 않는다

포인터를 움직이는 동안 매 프레임 커맨드를 쌓으면 되돌리기 한 번에 1px씩 움직인다. 드래그 중에는 씬을 직접 갱신하고(`actions.setScene`), 포인터를 뗄 때 누적 이동량으로 커맨드 하나를 히스토리에만 기록한다(`actions.record`).

### 회전은 각도 하나로, 히트 테스트는 역회전으로

도형마다 변환 행렬을 들리는 대신 `rotation` 각도 하나만 둔다. 지금 필요한 표현력에 skew나 비균등 변환이 없어서다.

덕분에 히트 테스트가 단순해진다. **점을 도형 중심 기준으로 역회전시킨 뒤 축 정렬 사각형으로 검사하면 끝이다**(`geometry.ts`의 `toLocal`). 회전이 붙었다고 해서 검사 로직을 다시 짜지 않아도 된다.

리사이즈도 같은 원리다. 회전한 도형을 월드 좌표에서 바로 계산하면 어긋나므로 세 단계로 나눈다 — 포인터를 로컬 좌표계로 옮기고, 축 정렬 상태에서 변을 갱신하고, 바뀐 중심을 다시 월드로 되돌린다. **마지막 보정이 없으면 회전된 도형을 리사이즈할 때 도형이 옆으로 미끄러진다.**

### 단일 리사이즈는 다중 리사이즈의 특수 케이스다

리사이즈의 대상은 도형이 아니라 **상자**(`Box` = 사각형 + 회전각)다. 하나만 골랐으면 도형 자신이 상자이고, 여럿을 골랐으면 회전 없는 공통 바운딩 박스가 상자다. `core/selection.ts`가 선택 상태를 이 상자 하나로 정리하고, 렌더러와 포인터 처리가 **같은 함수를 거친다** — 양쪽이 각자 상자를 계산하면 조건 하나만 어긋나도 보이는 핸들과 집히는 핸들이 조용히 벌어진다.

상자를 새로 계산한 뒤에는 각 도형이 상자 안에서의 상대 위치를 유지한 채 같은 비율로 커진다. 도형이 하나뿐이면 그 상대 위치가 늘 한가운데라, 상자 계산 결과가 곧 도형이 된다. 다중 선택을 붙이면서 단일 리사이즈 코드가 사라진 이유다.

### 회전이 섞인 다중 선택에서는 균등 스케일만 허용한다

공통 박스의 x와 y를 서로 다른 비율로 늘이면, 그 축에 비스듬히 놓인 사각형은 **평행사변형이 되어야 한다.** `rotation` 각도 하나로는 평행사변형을 표현할 수 없다. 제대로 풀려면 도형마다 변환 행렬을 들려야 하는데, 그건 히트 테스트("역회전 후 AABB 검사")부터 다시 짜야 하는 변경이다.

그래서 **90°의 배수인지**를 기준으로 갈랐다. 90°의 배수면 폭과 높이가 맞바뀔 뿐 사각형이 사각형으로 남으므로 비균등 스케일을 정확히 적용한다. 하나라도 배수가 아니면 종횡비를 강제로 고정해 두 축의 배율을 같게 만든다. 정확히 표현되는 범위를 최대한 넓히고, 나머지는 왜곡 대신 제약으로 처리하는 쪽을 골랐다.

### 리사이즈는 매 프레임 원본에서 다시 계산한다

직전 결과에 누적하면 두 가지가 깨진다. 부동소수 오차가 쌓이고, 드래그 도중 `Shift`를 눌렀다 떼는 조작을 되돌릴 수 없다. 드래그 시작 시점의 도형을 들고 있다가 매번 거기서 새로 계산한다.

### 화면 밖 도형은 그리지 않는다

Canvas는 화면 밖 도형을 알아서 잘라내지만, **잘라내기 전에 경로를 다 쌓는 비용은 그대로 든다.** 펜 획 하나가 수십 개의 `quadraticCurveTo`라 이 비용이 지배적이다. 그래서 그리기 전에 바운딩 박스로 걸러낸다 — 배율 1에서 한 프레임이 55.7ms에서 2.3ms가 됐다.

박스만 보고 자르면 안 된다. 굵은 획과 화살촉은 박스 밖으로 삐져나오므로 가장자리에서 잘려 보이다가 튀어 들어온다. **얼마나 삐져나오는지는 도형만 안다** — 화살촉 크기는 `line.ts`의 상수이고 필압 획의 최대 굵기는 `path.ts`의 규칙이다. 그래서 레지스트리에 `renderPad`가 생겼다.

### 공간 인덱스는 후보만 좁히고, 판정은 그대로 둔다

quadtree가 하는 일은 "이 근처에 뭐가 있나"까지다. 최종 판정은 여전히 `hitTest`가 한다. 이 분업이 중요한 이유는 **인덱스가 들고 있는 사각형이 실제 판정 영역보다 넉넉하기만 하면 되기** 때문이다 — 모자라면 도형을 놓치지만, 남으면 후보가 몇 개 늘 뿐이다. 이 비대칭 덕분에 여유 폭을 대충 크게 잡아도 안전하다.

**인덱스의 실패 방식은 느려지는 것이 아니라 조용히 틀리는 것이다.** 얇은 선 하나가 후보에서 빠져도 화면에는 아무 표시가 나지 않는다. 그래서 얇은 도형의 판정 여유(`HIT_PAD_PX`)는 도형 모듈 안에 숨기지 않고 `core/types.ts`에 한 번만 정의하고, 벤치마크가 매번 전체 훑기와 결과를 대조한다.

컬링도 같은 이유로 매번 검증한다. **버린 도형만 모아 다시 그려서** 한 점이라도 칠해지면 버리면 안 될 것이 섞여 있었다는 뜻이다. 이때 반드시 **더 넓은 화면**에 그려야 한다 — 좁은 화면 그대로 그리면 방금 버린 도형이 또 걸러져서 검사가 언제나 통과한다. 컬링을 일부러 망가뜨렸는데도 통과하는 것을 보고 알아챘다.

인덱스는 씬 객체의 동일성으로 캐시하고 **질의할 때 만든다.** 드래그 중에는 매 프레임 새 씬이 생기지만 그때는 아무도 질의하지 않는다 — 픽은 누를 때, 마퀴는 씬이 그대로인 동안에만 돈다. 미리 만들면 쓰지도 않을 인덱스를 매 프레임 세우게 된다.

### 움직이는 것만 다시 그린다 — 캔버스를 둘로 나눈다

컬링으로 한 프레임이 2.3ms까지 내려왔지만, 그중 상당 부분이 **움직이지 않은 도형을 매번 다시 그리는 비용**이었다. 도형 하나를 끄는 동안 나머지 수백 개는 픽셀 한 점 바뀌지 않는데도 전부 다시 그려진다.

그래서 캔버스를 둘 겹쳤다. 아래(정적 레이어)에는 움직이지 않는 도형이, 위(활성 레이어)에는 조작 중인 도형·생성 중인 draft·선택 UI가 그려진다. 합치는 일은 브라우저 컴포지터가 하므로 JS는 바뀐 쪽만 그리면 된다. **1만 개에서 드래그 한 프레임이 2.3ms → 0.2ms다.**

같이 사라진 것이 하나 더 있다. 도형 수에 비례하던 컬링 순회가 정적 레이어에만 남아, 드래그 중에는 프레임 비용이 **도형 수와 무관해졌다.**

**어려운 것은 그리기가 아니라 "언제 낡았는가"였다.** 정적 레이어는 캐시라, 다시 그려야 할 때를 놓치면 화면에 옛 픽셀이 남고 아무 오류도 나지 않는다. 그런데 씬 참조로는 판단할 수 없다 — 드래그 중에는 매 프레임 새 씬이 만들어지지만 실제로 바뀐 것은 잡고 있는 도형뿐이라, 씬이 달라졌다고 다시 그리면 레이어를 나눈 이득이 통째로 사라진다.

**어떤 종류의 변경인지 아는 것은 스토어뿐이었다.** M0에서 만들어둔 `execute`/`setScene`/`record` 3분기가 그대로 답이 됐다 — 히스토리에 남는 변경은 정적 레이어를 무효화하고, 드래그 중의 `setScene`은 그러지 않는다. 대신 조작을 시작할 때 **"포인터를 뗄 때까지 바뀔 도형은 이것뿐"**이라고 선언한다(`state.active`). 성능 최적화가 히스토리 설계에 기대게 될 줄은 예상하지 못했다.

대가는 **조작 중인 도형이 z-order를 무시하고 맨 앞에 뜬다**는 것이다. 정확히 하려면 매 프레임 전체 순서를 다시 세워야 해서 나눈 이유가 사라진다. 회전이 섞인 다중 리사이즈에서는 "표현할 수 없으면 왜곡하지 말고 제약한다"를 골랐는데 여기서는 반대로 갔다 — 차이는 **되돌릴 수 있는가**다. 회전 왜곡은 문서에 남지만 이 어긋남은 포인터를 떼는 순간 사라진다.

여기도 실패 방식이 "느려짐"이 아니라 "조용히 틀림"이라 벤치마크가 매번 검증한다. **정적 레이어만** 통짜 렌더와 맞대 보는데, 활성 레이어는 매 프레임 새로 그려지므로 애초에 낡을 수가 없기 때문이다. 대상을 좁히자 두 캔버스를 합성할 때 생기는 알파 반올림 오차(1~2/255)가 사라져 **임계값 없이** 비교할 수 있게 됐다.

### 생성 중인 도형은 씬 밖에 둔다

드래그로 도형을 그리는 동안의 미완성 도형은 `state.draft`로 따로 관리한다. 씬에 미리 넣으면 확정 전 상태가 히스토리와 z-order에 섞여 들어간다. 확정 전이라 z-order가 없다는 성질은 레이어 분리에서도 편했다 — draft는 늘 활성 레이어에 있으면 된다.
