# Architecture Decision Records

## 철학

**틀린 숫자보다 없는 숫자가 낫다.** 이 제품이 파는 것은 "몰랐던 사실"인데, 사실이 아니면 가치가 음수다. 그래서 모르는 것은 "미분류"로 남기고 추측으로 채우지 않는다.

**저장하지 않는다.** 개인 금융정보의 보관 책임을 지지 않는다. 그 대가로 새로고침하면 리포트가 사라지고, 재집계를 클라이언트가 떠안는다.

각 결정의 상세 근거는 `DESIGN.md`에 있다. 아래는 요약이다.

---

### ADR-001: 입력은 CSV 전용
**결정**: xlsx를 지원하지 않는다. 사용자가 스프레드시트로 열어 CSV로 내보내게 안내한다.
**이유**: 토스뱅크가 주는 `.xlsx`는 ECMA-376으로 **암호화**된 OLE2 파일이다(`EncryptionInfo` v4.2). 일반 xlsx 파서로 열리지 않는다. 지원하려면 복호화 라이브러리와 비밀번호 입력 UI가 필요한데, 그 비밀번호는 통상 생년월일·주민번호 앞자리다. 파일은 저장하지 않으면서 그 파일을 여는 열쇠가 개인 식별번호인 구조는 방어할 수 없다.
**트레이드오프**: 사용자에게 변환 3단계를 떠넘긴다. 첫 진입 이탈이 늘어난다. (DESIGN.md 2.8)

### ADR-002: 서버에서 처리하되 저장하지 않는다
**결정**: 원본 파일 전체를 서버로 보내 파싱·분류·요약까지 하고, 응답 후 폐기한다.
**이유**: OpenAI API 키를 브라우저에 노출할 수 없어 서버가 필요하다. 저장하지 않으면 보관기간·파기절차·유출 영향범위가 통째로 사라진다.
**트레이드오프**: 새로고침하면 리포트가 사라진다. PDF 내보내기로 완화한다. (DESIGN.md 4.1)

### ADR-003: 응답에 거래 배열을 포함하고 재집계는 클라이언트가 한다
**결정**: 서버는 `{ transactions, report }`를 함께 응답한다. 사용자 보정 시 클라이언트가 `lib/analyze.ts`로 재집계한다.
**이유**: 저장하지 않으므로 재집계할 원본이 서버에 없다. 사용자 보정(출금 카테고리, `소비 아님`)을 반영하려면 재업로드를 시키거나 클라이언트가 데이터를 들고 있어야 한다.
**트레이드오프**: "클라이언트를 단순하게"라는 원칙이 부분 후퇴한다. `lib/`는 순수 함수여야 한다는 제약이 생긴다. (DESIGN.md 4.2)

### ADR-004: 통계가 주인공, LLM은 곁들이
**결정**: 모든 숫자는 코드가 계산한다. LLM은 미분류 가맹점명 분류와 요약 문장 작성만 한다.
**이유**: 금액을 지어내는 실패가 이 도메인에서 치명적이다. 분류에는 금액이 필요 없으므로 아예 보내지 않아, LLM이 숫자를 만질 여지 자체를 없앤다.
**트레이드오프**: LLM으로 한 번에 해결할 수 있을 일을 규칙과 코드로 나눠 짜야 한다. (DESIGN.md 4.3)

### ADR-005: 취소 쌍은 시간 상한 없이 1:1로 매칭해 양쪽 제외
**결정**: `적요 + 절대금액` 키로, 취소 행마다 가장 가까운 **이전** 미매칭 결제 1건과만 짝짓고 둘 다 제외한다. 경과 시간에 상한을 두지 않는다.
**이유**: 부호만 상쇄하면 총액은 맞지만 가맹점별 순위가 틀린다. 샘플의 취소 간격이 24초와 **42시간**이라 "같은 날" 류의 상한을 두면 후자를 놓친다.
**트레이드오프**: 같은 가맹점·같은 금액의 별개 환불을 취소로 오탐할 수 있다. 기간이 길수록 확률이 커진다. (DESIGN.md 4.6, 8.6)

### ADR-006: 이벤트를 카테고리와 별개 축으로 둔다
**결정**: 여행 같은 이벤트는 카테고리 분류와 독립적으로 묶어 제시한다. `여행`은 카테고리 목록에 넣지 않는다.
**이유**: 카테고리로만 나누면 항공권→교통, 숙박→숙박으로 흩어져 "여행 한 번에 78만원"이라는 사실이 사라진다. 이것이 이 데이터가 주는 가장 센 신호다.
**트레이드오프**: 같은 돈이 두 축에 중복 계상된다. 리포트에 그 사실을 고지해야 한다. (DESIGN.md 4.9)

### ADR-007: 사람별 리포트를 만들지 않는다
**결정**: 공동명의 계좌여도 전체 리포트 하나만 만든다.
**이유**: 카드 거래에 사용자 구분 필드가 없다. 샘플의 체크카드결제 25건 중 사용자를 식별할 수 있는 건은 0건이다. 만들면 소비 207만원이 어디에도 귀속되지 않아 두 리포트 모두 빈 껍데기가 된다.
**트레이드오프**: 공동 계좌 사용자의 "누가 더 썼나" 요구를 못 받는다. 대신 요약에 2인 합계임을 고지한다. (DESIGN.md 4.8)

### ADR-008: PDF는 브라우저 인쇄로만 만든다
**결정**: `@media print` 스타일만 작성한다. 서버 렌더링 PDF(Puppeteer 등)를 쓰지 않는다.
**이유**: 저장하지 않는 정책에 헤드리스 브라우저는 과한 장치다. 인쇄는 의존성 0이다.
**트레이드오프**: 출력 레이아웃 제어권이 브라우저에 있다. 페이지 나눔이 완벽하지 않을 수 있다. (DESIGN.md 4.12)

### ADR-009: 테스트는 `src/lib/`만
**결정**: 순수 로직에만 TDD를 요구한다. UI 컴포넌트와 페이지에는 테스트를 요구하지 않는다.
**이유**: 파싱·취소 탐지·분류·집계가 조용히 틀리면 리포트 전체가 틀리는데 화면상으로는 그럴듯해 보인다. UI는 눈으로 확인된다.
**트레이드오프**: 렌더 회귀를 잡지 못한다. 실험 프로젝트의 속도를 위해 감수한다. (DESIGN.md 6절)

### ADR-010: 실제 거래내역 픽스처를 커밋하지 않는다
**결정**: `fixtures/`를 gitignore하고, 파일이 없으면 픽스처 의존 테스트를 skip한다.
**이유**: 실명·계좌번호·실제 소비내역이 든 파일이다. 공개 이력을 갖는 저장소에 한 번 커밋되면 영구 기록이다.
**트레이드오프**: CI에서 핵심 테스트가 돌지 않는다. 기댓값을 `DESIGN.md` 5.2에 상수로 남겨 다른 환경에서 재현 가능하게 한다. (DESIGN.md 7.1)
