# spend-report — 설계 문서

> **상태:** 구현 전 설계안. 아직 코드는 한 줄도 없다.
> **작성일:** 2026-08-19 (1차) / 2026-08-19 (2차 개정 — 검토 반영)
> **검토자에게:** 이 문서는 구현 착수 전 검토를 받기 위한 것이다. 결정마다 근거를 붙였으니 근거를 공격해 달라. 마지막 절에 특히 의심스러운 지점을 따로 모아 두었다.

> **2차 개정 요약**
> - 입력 파일 전제가 실증적으로 틀린 것이 확인돼 결정 3이 바뀌었다 — 원본 xlsx는 암호화돼 있다(2.8)
> - 아키텍처 모순 1건 해소(4.2), 리포트 설계 오류 1건 수정(5.2/5.3), 취소 매칭 명세 보강(4.6)
> - 5.2 기댓값을 실데이터로 전수 검산했다. 값은 맞았지만 **4.9의 이벤트 알고리즘으로는 그 값이 나오지 않는다**는 것이 드러났다(8.3)
> - 프로젝트 구조를 `harness` 템플릿 기준으로 다시 세웠다(6절)

## 1. 배경

### 저장소 맥락

`ai-feature-lab`은 AI 기능·아이디어를 독립 프로젝트로 실험하는 모노레포다. 각 프로젝트는 자체 소스·설정·문서를 자기 폴더 안에서 관리하며, **서로 공유하는 코드나 설계는 없다.**

`spend-report`가 저장소에서 유일하게 참조하는 것은 `harness`다. Harness는 문서 기반 phase/step 워크플로우를 자동 실행하는 프레임워크로, 이 프로젝트는 그 **템플릿을 복사해 채워 쓴다**(6절). 다른 프로젝트의 코드·규칙·패턴은 가져오지 않는다.

### 이 프로젝트의 목적

은행 거래내역 파일을 업로드하면 소비 패턴 분석 리포트를 한 화면으로 보여준다.

부차 목적이 하나 더 있다: `harness`를 새 프로젝트에 태워 **특정 프로젝트 전용 스크립트가 아니라 재사용 가능한 프레임워크임을 검증**한다. harness의 문서 템플릿(`CLAUDE.md`, `docs/PRD.md`, `docs/ARCHITECTURE.md`, `docs/ADR.md`, `docs/UI_GUIDE.md`)은 모두 `{플레이스홀더}` 상태이며, 아직 그것을 실제로 채워 완주한 사례가 확인되지 않았다.

### 리포트의 성격 — 회고형이 아니라 발견형

"지난달에 어디에 얼마 썼나"(회고형)는 **카드사·은행 앱이 이미 공짜로 제공한다.** 사용자가 파일을 직접 내려받아 업로드하는 수고를 정당화하려면 그 이상이어야 한다.

따라서 리포트의 주인공은 **사용자가 몰랐던 것**이다:
- 반복 결제 — 생각보다 자주 쓰고 있는 곳
- 이벤트성 지출 — 여행 한 번이 그 달 소비의 몇 %였는지
- 집중도 — 상위 몇 건이 전체를 좌우하는지
- 취소 누락 — 취소됐는데 지출로 착각하고 있던 건

회고형 정보(카테고리별 지출)는 발견을 뒷받침하는 **근거**로 깔되, 주인공 자리를 주지 않는다.

## 2. 입력 데이터 사양

> **중요:** 이 절은 추측이 아니다. 실제 샘플 파일을 읽고 확인한 사실이다.
> 샘플: 토스뱅크 거래내역 (조회기간 2026.08.01–08.15, 실제 거래 08.01–08.14, 데이터 34행, UTF-8)
> **단, 아래 2.1~2.7은 xlsx를 스프레드시트로 열어 CSV로 내보낸 결과에 대한 사양이다.** 원본 xlsx 자체는 2.8 참조.

### 2.1 파일 구조

```
1~8줄   메타/안내행
          ,토스뱅크 거래내역,,,,,,,
          ,성명,장민우 외 1인,,,,,,
          ,계좌번호,****-****-8269,,,,,,
          ,조회기간,2026.08.01 - 2026.08.15,,,,,,
          ,,,,,,,,
          ,※ 본 거래내역은 법적효력이 없는 참고용 문서입니다.,,,,,,,
          ,※ 거래내역은 10만 개까지만 표시됩니다. ...,,,,,,,
          ,,,,,,,,
9줄     헤더
          ,거래 일시,적요,거래 유형,거래 기관,계좌번호,거래 금액,거래 후 잔액,메모
10줄~   데이터
          ,2026.08.14 18:56:16,쿠팡이츠,체크카드결제,,,"-39,000","6,769,423",
```

### 2.2 파서가 반드시 처리해야 하는 것

> **전제:** 아래는 **CSV 입력 전용 사양**이다. 3·4번은 CSV가 모든 셀을 문자열로 주기 때문에 필요한 처리이며, xlsx를 직접 읽는 경로에서는 셀이 number/date serial로 오므로 별도 정규화가 필요하다. 이번 범위는 CSV 전용이므로(결정 3) 해당 경로는 만들지 않는다.

| # | 사항 | 근거 |
|---|---|---|
| 1 | **첫 컬럼은 전부 빈 더미** | 9컬럼처럼 보이지만 실데이터는 2~9번째. 모든 행이 `,`로 시작한다 |
| 2 | **헤더 줄 번호를 고정하지 말 것** | `거래 일시`가 포함된 행을 찾아 헤더로 삼는다. 조회기간·계좌 종류에 따라 안내행 수가 달라질 수 있다 |
| 3 | **날짜 형식** `2026.08.14 20:32:16` | 점 구분, 초 단위. `Date` 파싱이 그냥은 안 된다 |
| 4 | **금액이 콤마 포함 문자열** | `"-39,000"`. **부호가 입출금을 구분한다** (음수=출금) |
| 5 | **업종/카테고리 컬럼이 없다** | 아래 2.3 참조 — 이 설계의 가장 중요한 제약 |
| 6 | **헤더의 성명·계좌번호는 버린다** | 사람별 리포트를 만들지 않으므로 쓸 데가 없다 (4.8 참조) |

### 2.3 `거래 유형`은 카테고리가 아니다

이 파일에서 가장 오해하기 쉬운 지점이다. `거래 유형` 컬럼의 실제 분포:

```
체크카드결제  25건   (음수 23 + 취소 양수 2)
입금           3건
출금           2건
프로모션입금    2건
모임원송금      1건
이자입금       1건
                    합계 34건 = 데이터 행 수
```

이건 **결제 수단**이지 식비/교통/쇼핑 같은 업종이 아니다. **업종 컬럼은 파일에 존재하지 않는다.** 소비 카테고리는 `적요` 문자열과 `메모`에서 추론하는 수밖에 없다.

이걸 카테고리로 착각하면 "체크카드결제 25건"짜리 무의미한 파이차트가 나온다.

### 2.4 `적요`의 실제 모습

```
쿠팡이츠                        ← 규칙 사전으로 분류 가능
(주)이마트 구로점                 ← 법인 접두사 + 지점명
씨제이올리브영(주)신림중앙점         ← 한글 음차 법인명 + 지점명
탐앤탐스삼모타워신림역점            ← 브랜드+건물+역명이 붙어 있음
막불감동 / 열매상회 / 영광과일       ← 소상공인. 사전으로 절대 못 잡음
신주옥미 신림역점                 ← 상호만으로 업종 추정 어려움
엔에이치엔케이씨피 ㈜              ← NHN KCP. 결제대행사(PG)
토스페이_TOSS                   ← PG 경유. 실가맹점 불명
주식회사 놀유니버스                ← 야놀자 자회사. 이름만으론 모름
쿠팡(쿠페이)                    ← 브랜드는 알아도 품목은 모름
```

**PG 경유 건은 적요만으로는 원리적으로 분류 불가능하다.** `엔에이치엔케이씨피 ㈜ -218,500원`이 무엇인지 이 컬럼만 봐서는 영원히 알 수 없다.

**따라서 PG 적요를 가맹점 이름처럼 다루면 안 된다.** 리포트 표시명 규칙은 5.2, 반복 결제 집계에서의 제외는 4.4를 보라.

### 2.5 `메모`가 PG 문제를 푼다

메모는 사용자 자유 입력이며, 샘플에서 13건이 채워져 있다. 그리고 **PG 건들이 정확히 메모로 해결된다:**

```
엔에이치엔케이씨피 ㈜  -218,500  →  메모: "제주도 2일 숙박비"      → 숙박
토스페이_TOSS         -71,300  →  메모: "제주도 렌트비용"        → 교통
토스페이_TOSS         -50,630  →  메모: "제주고 1일 숙박비"      → 숙박   ← "제주고"는 사용자 오타
아시아나항공          -163,000  →  메모: "김포>제주 항공권 2인"    → 교통
대한항공             -275,000  →  메모: "제주>김포 항공권 2인"    → 교통
주식회사 놀유니버스      -2,000  →  메모: "항공권예약 대행수수료"   → 수수료/기타   ← 2건 (아래 참조)
```

> 위 6건은 **카테고리 축** 매핑이다. 이들이 하나의 여행이라는 사실은 카테고리가 아니라 **이벤트 축**이 담는다(결정 9, 4.9). 1차 문서에서 놀유니버스를 `여행` 카테고리로 매핑했던 것은 두 축을 섞은 오류라 고쳤다 — `여행`은 카테고리 목록(9절)에 없다.

**놀유니버스 수수료 2건은 메모에 지명이 없다.** 항공권 결제 바로 옆에 초 단위로 붙어 있다:

```
20:08:19  대한항공        -275,000  "제주>김포 항공권 2인"
20:08:28  놀유니버스        -2,000  "항공권예약 대행수수료"   ← 9초 뒤
20:08:30  아시아나항공     -163,000  "김포>제주 항공권 2인"
20:08:41  놀유니버스        -2,000  "항공권예약 대행수수료"   ← 11초 뒤
```

메모에 `제주`가 없으므로 **키워드 매칭만으로는 이벤트에서 누락된다.** 이 4,000원이 8.3 알고리즘 선택의 결정적 사례다.

**그래서 분류 우선순위에서 메모가 적요보다 앞선다.**

단, 한계가 둘 있다.

1. **메모도 자연어다.** `"제주도 2일 숙박비" → 숙박`을 만들려면 메모 문자열에도 키워드 규칙이나 LLM이 필요하다. 그 규칙은 아직 정하지 않았다(8.3).
2. **메모 13건 중 11건이 제주·울진 여행 정산이다.** 이 사용자는 여행 때만 메모를 쓴다. 일상 소비(쿠팡이츠 4건, 이마트, 올리브영, 탐앤탐스, 세계과자할인점)에는 메모가 없다. 메모에 의존하는 설계는 여행 같은 이벤트에는 강하고 일상 소비에는 무력하다.

### 2.6 취소 쌍

샘플에 취소 쌍이 2건 있다. 같은 적요, 같은 절대금액, 반대 부호다.

```
롯데시네마_티켓_토스페이_TOSS   36,000원
    2026.08.14 20:31:52  -36,000   (결제)
    2026.08.14 20:32:16  +36,000   (취소)   ← 24초 간격

(주)그린카                 267,750원
    2026.08.10 01:44  -267,750   (결제)   메모: "울진여행 렌트카비"
    2026.08.11 19:50  +267,750   (취소)   메모: "울진여행 렌트카비 취소"
                                          ← 42시간 간격
```

**"같은 날 취소" 같은 상식적 규칙으로는 그린카를 놓친다.** 경과 시간에 상한을 두지 않는다. 매칭 알고리즘 명세는 4.6.

메모의 `취소` 키워드는 보조 신호로 쓸 수 있다.

### 2.7 "소비"의 정의에 따라 총액이 2배 넘게 흔들린다

```
체크카드결제 출금만                     2,175,560원
  └ 취소 쌍 2건 제외 후                 1,871,810원   (-303,750 = 36,000 + 267,750)
    └ + 출금 206,000                  2,077,810원   ← 채택
      └ + 모임원송금 1,859,497         3,937,307원
```

이 계좌는 **공동명의**(`성명: 장민우 외 1인`)이고 `여행비` 정산 입출금까지 섞여 있어 자동 판정이 불가능하다. 사람이 정의해 줘야 한다.

참고로 소비가 아닌 항목들:
```
장민우      입금      2,282,000   메모: "8월 생활비"
박상은      입금      2,284,000   메모: "8월 생활비"
여행비      입금        782,430   메모: "제주 왕복항공권/숙소3일치/차렌트비용"
장민우   모임원송금   -1,859,497   메모: "냉장고 구매"
통장 이자   이자입금         365
카드 캐시백 프로모션입금  100 / 500
```

### 2.8 원본 xlsx는 암호로 잠겨 있다 ⚠️ 1차 문서에서 틀렸던 지점

1차 문서는 파일명(`토스뱅크_거래내역.xlsx - 토스뱅크 거래내역.csv`)만 보고 "앱이 주는 건 xlsx이고 이건 스프레드시트로 열어 CSV로 내보낸 것"이라고 관찰했다. 관찰은 맞았지만 **왜 CSV로 내보낼 수밖에 없었는지**를 놓쳤다.

실물을 열어 확인한 결과:

```
file        →  CDFV2 Encrypted        (매직 D0CF11E0 = OLE2 복합문서, ZIP 아님)
OLE 스트림   →  EncryptionInfo
                EncryptedPackage
                \x06DataSpaces/.../StrongEncryptionDataSpace
EncryptionInfo  버전 4.2 = ECMA-376 Standard Encryption
                "Microsoft Enhanced RSA and AES Cryptographic Provider"
```

**토스뱅크가 내려주는 xlsx는 비밀번호로 암호화된 파일이다.** 확장자만 `.xlsx`일 뿐 OOXML(ZIP) 컨테이너가 아니라 암호화된 OLE2 컨테이너다.

따라서:

- **SheetJS 커뮤니티 에디션·`exceljs` 모두 이 파일을 열지 못한다.** "xlsx를 지원한다"는 라이브러리를 붙여도 첫 바이트에서 실패한다
- 지원하려면 ECMA-376 복호화 단계와 **비밀번호 입력 UI**가 선행돼야 한다
- 그 비밀번호는 통상 생년월일·주민번호 앞자리다. 그걸 서버로 전송하는 순간 **4.1의 프라이버시 기조와 정면으로 충돌한다.** 파일은 저장하지 않는데 그 파일을 여는 열쇠가 개인 식별번호라는 구조는 방어하기 어렵다

**결론: CSV 전용은 회피가 아니라 정합적인 선택이다.** xlsx를 지원하는 쪽이 오히려 개인정보 노출면을 넓힌다. 사용자에게는 업로드 화면에서 변환 3단계를 안내한다(5.3).

## 4. 결정의 근거

### 4.1 서버 처리, 저장 안 함 (결정 1)

거래내역은 가맹점·금액·날짜가 붙은 개인 금융정보다. 저장하지 않으면 보관기간·파기절차·유출 시 영향 범위가 통째로 사라진다. 실험 저장소가 지고 싶지 않은 종류의 책임이다.

서버가 필요한 이유는 **LLM API 키를 브라우저에 노출할 수 없어서**다.

> **주의:** "저장하지 않음"이 "외부로 나가지 않음"은 아니다. 미분류 가맹점명은 OpenAI로 전송된다(4.4). 이쪽이 실질적으로 더 큰 노출면이며 8.1에서 다룬다.
>
> CSV 전용으로 결정하면서(결정 3) 파일 비밀번호를 서버로 받는 경로는 사라졌다.

### 4.2 원본 전체 전송, 재집계는 클라이언트 (결정 2)

서버가 파싱·집계·LLM을 모두 담당하면 클라이언트가 단순해진다. 대안(집계 결과만 전송)은 전송량을 최소화하지만 클라이언트에 파싱·집계 로직이 전부 들어가야 한다.

**단, 1차 문서에는 모순이 있었다.** 결정 1(저장 안 함) + 결정 2(서버 전담) + 4.5(사용자 입력 후 리포트 반영)는 동시에 성립하지 않는다. 사용자가 출금 카테고리를 입력하면 재집계가 필요한데, 서버는 원본을 이미 버렸고 클라이언트에는 집계 로직이 없다.

**해소:**

> 서버는 파싱·취소탐지·분류까지 수행하고 **정규화된 거래 배열 + 집계 결과를 함께** 응답한다.
> 클라이언트는 거래 배열을 메모리에 들고, 사용자 입력(출금 카테고리, 소비 여부)이 바뀌면 **클라이언트에서 재집계**한다.
> 재집계 로직은 `src/lib/analyze.ts`를 클라이언트에서도 import해 공유한다 (순수 함수라 가능).

대가를 분명히 적어 둔다: 결정 2의 근거였던 "클라이언트 단순화"가 부분적으로 후퇴한다. 다만 파싱·LLM 호출은 여전히 서버에 남으므로 결정 2의 핵심(무거운 의존성과 비밀은 서버)은 유지된다. 재업로드를 요구하는 대안보다 사용자 경험이 낫다.

### 4.3 통계가 주인공, LLM은 곁들이 (결정 4)

**금액 계산을 LLM에 시키면 안 된다.** 없는 합계를 그럴듯하게 지어내는 실패 양식이 이 도메인에서는 치명적이다. 숫자는 전부 코드가 계산하고, LLM은 (a) 미분류 가맹점명 분류, (b) 계산된 집계치를 문장으로 옮기기 — 두 가지 좁은 일만 한다.

### 4.4 분류 파이프라인 (결정 5)

메모 → 규칙 → LLM → 미분류 순으로 시도하고 먼저 맞는 데서 멈춘다.

- **메모 우선**: 2.5에서 본 대로 PG 건을 유일하게 푼다. 단 메모도 자연어라 키워드 규칙이 필요하다 — 그 규칙은 미정(8.3)
- **규칙 사전**: 쿠팡이츠·이마트·올리브영·탐앤탐스는 공짜로 처리된다. LLM 호출을 아낀다
- **LLM**: `막불감동`·`영광과일`·`열매상회`·`신주옥미 신림역점` 같은 소상공인은 사전으로 절대 못 잡는다. 한국 상호 추론이 필요하다
- **미분류**: 그래도 모르면 "미분류"로 남기고 그 비중을 리포트에 표시한다. **추측으로 채우지 않는다**

**PG 사전을 별도로 둔다.** `토스페이_TOSS`, `엔에이치엔케이씨피`, `KG이니시스` 등 결제대행사 적요는 가맹점이 아니라 결제 경로다. 이 목록에 걸리면:
- 카테고리 분류는 메모에만 의존한다 (규칙·LLM 단계로 내려보내지 않는다 — 적요에 정보가 없으므로 LLM은 추측만 한다)
- **반복 결제 집계에서 제외한다** (5.2)
- 리포트 표시명을 메모 기반으로 치환한다 (5.2)

**LLM에는 미분류 적요 목록만 보내고 금액은 보내지 않는다.** 분류에 금액이 필요 없고, 보내지 않으면 LLM이 금액을 만질 여지 자체가 없다. (다만 적요 자체가 민감할 수 있다 — 8.1)

### 4.5 출금과 고액 미상세 건은 사용자에게 넘긴다 (결정 5 — 4.4의 예외)

출금은 메모가 있으면 그것을 쓰고, 없으면 `알 수 없음`으로 표시해 **사용자가 직접 지정**하도록 유도한다.

샘플의 출금 2건이 둘 다 메모가 없다:
```
박상은서울주민   -6,000
여행비        -200,000
```
현금이 어디 쓰였는지 파일에 정보가 없다. 추론이 불가능하므로 사용자에게 넘긴다.

**선택지에 `소비 아님(제외)`을 포함한다.** 이게 없으면 안 된다: `여행비 -200,000`은 공동명의 정산 계좌의 정산 이체일 가능성이 크고, 그 금액은 소비 총액 2,077,810원의 **9.6%**다. 4.7이 "송금은 소비 아님"이라고 했지만 출금 형태로 나간 정산금은 그 규칙에 걸리지 않는다. 사용자가 빼면 총액에서 빠진다(재집계는 4.2).

**대상을 출금에 한정하지 않는다.** 상위 지출 중 카테고리가 확정되지 않은 고액 건도 같은 입력 대상으로 올린다. 근거는 5.2 — 이 샘플에서 **1위 지출 `쿠팡(쿠페이) 769,900원`(전체의 37%)의 품목을 알 수 없다.** 2.4가 직접 인정한 한계다. 이걸 방치하면 발견형 리포트의 1번 발견이 "쿠팡에서 77만원 썼다, 뭔지는 모름"이 된다.

### 4.6 취소 쌍 제외 (결정 7)

부호만 더하면 수학적으로는 상쇄되지만, **가맹점별 순위가 틀린다.** "그린카에 26.8만원 썼다"가 상위 지출로 올라온다. 양쪽 모두 리포트에서 빼고, 뺀 사실을 명시한다.

**매칭 알고리즘:**

1. 후보 키 = `적요` + `절대금액`
2. **1:1 그리디 매칭** — 취소 행(양수)마다 같은 키를 가진 **가장 가까운 이전 미매칭 결제 1건**과만 짝짓고, 짝지은 결제는 소진 처리한다
3. **시간 순서 제약** — `취소 시각 > 결제 시각`. 경과 시간의 **상한은 두지 않는다**(2.6의 42시간 사례). 상한이 없는 것과 순서 제약이 없는 것은 다른 문제다
4. 짝지어진 두 행 모두 제외하고, 제외 건수·금액을 리포트 요약에 표시한다

1차 문서의 "적요+절대금액+반대부호 → 양쪽 제외"라는 표현은 다대다 상황(같은 가맹점 -10,000이 3건, +10,000이 1건)에서 3건을 모두 지우는 과잉 삭제로 읽힌다. 그래서 위와 같이 고쳤다.

한계는 8.6에 적어 둔다.

### 4.7 소비 = 카드 + 출금 (결정 6)

카드결제만 보면 실제 나간 돈을 놓치고(출금한 현금도 결국 쓴 돈), 송금까지 넣으면 내 다른 계좌로 옮긴 돈이 소비로 잡힌다. 샘플의 `장민우 모임원송금 -1,859,497 (냉장고 구매)`이 그 경계 사례다.

출금 중 정산 이체가 섞이는 문제는 4.5의 사용자 입력으로 처리한다.

### 4.8 사람별 리포트를 만들지 않는 이유 (결정 8)

**데이터에 귀속 근거가 없다.**

```
체크카드결제 25건 중 사용자를 식별할 수 있는 건:  0건
```

실명이 등장하는 건 4건뿐이고 전부 입출금이다:
```
장민우      입금      2,282,000   메모: "8월 생활비"
박상은      입금      2,284,000   메모: "8월 생활비"
장민우   모임원송금   -1,859,497   메모: "냉장고 구매"
박상은서울주민 출금       -6,000
```

이건 **누가 이 계좌에 돈을 넣었나**지 **누가 썼나**가 아니다. 공동명의 계좌의 카드 거래에는 사용자 구분 필드가 존재하지 않는다.

사람별 리포트를 만들면 소비 207만원이 어느 쪽에도 귀속되지 않아 **두 리포트 모두 빈 껍데기**가 되고 전체 리포트만 내용을 갖는다. 만들 수는 있지만 만드는 순간 거짓말이 된다.

**대신 그 결론을 리포트에 드러낸다.** 이 숫자가 2인 합계라는 사실은 요약 섹션에 고지한다(5.3). 안 적으면 사용자는 이걸 자기 혼자 쓴 돈으로 읽는다.

(각자 개인 계좌 파일을 따로 업로드하는 방식은 가능하나, 이번 범위에서 제외했다.)

### 4.9 이벤트 축 (결정 9)

메모 13건 중 11건이 제주·울진 여행이다. 이걸 카테고리로만 분류하면 항공권→교통, 숙박→숙박, 렌트→교통으로 **흩어져서 "여행 한 번에 78만원 썼다"는 사실이 사라진다.**

메모의 반복 키워드로 묶어 카테고리와 별개 축으로 제시한다. 발견형 리포트에서 이 파일이 주는 가장 센 신호다.

**"전체 대비 %"를 단독 지표로 쓰지 않는다.** 그 비율은 파일 기간에 반비례해서 흔들린다 — 같은 여행이 11일치 파일에서는 37.7%, 6개월치 파일에서는 6%가 된다. 4.10이 3~6개월치를 권하므로 이 충돌은 실제로 일어난다.

**대신 이렇게 쓴다:**

```
제주 여행 — 7건 782,430원, 2026.08.12 하루에 결제
  같은 파일 기간(11일) 소비의 37.7%
```

즉 **절대값(금액·건수)을 앞에 놓고**, 비율은 "무엇에 대한 비율인지"를 붙여 보조로 단다. 사용자가 다른 기간의 파일을 올려도 앞의 두 값은 그대로 비교된다.

> **거래일은 여행 기간이 아니다.** 이 이벤트의 7건은 **전부 2026.08.12 하루에** 찍혀 있다. 항공·숙박·렌트를 같은 날 예약했기 때문이다. 여행이 언제 며칠짜리였는지는 거래 데이터에 없고 메모 텍스트(`숙소3일치`, `2일 숙박비`, `1일 숙박비`)에만 있다.
>
> 그래서 **"이벤트 기간 일평균" 류의 지표는 만들 수 없다.** 기간 독립적이라 매력적이지만 분모가 존재하지 않는다. 억지로 거래일 범위를 쓰면 "하루에 78만원"이 되어 사실을 왜곡한다.

### 4.10 기간 (결정 10)

샘플은 **11일치**다(조회기간 헤더는 8.01–8.15지만 실제 거래는 8.01–8.14).

이 기간으로 **불가능한 발견**:
- 전월 대비 증감
- 추세 ("3개월째 증가")
- **구독 탐지** — 구독은 월 1회 결제라 11일치엔 한 번만 찍히고, 한 번은 반복이 아니다. 최소 2~3개월치가 필요하다

해결: 토스뱅크에서 조회기간을 길게(3~6개월) 잡아 받으면 한 파일에 다 들어온다. 구현 비용 0이다. 대신 **헤더의 조회기간을 읽어 짧으면 리포트에 한계를 명시**한다.

> 이 권장이 5.2의 기댓값과 충돌한다. 5.2는 **11일 샘플 전용 회귀 픽스처**이며 권장 사용 기간과 분리해서 읽어야 한다.

**용어를 하나로 통일한다.** 리포트에서는 `반복 결제`만 쓰고 `구독`은 쓰지 않는다. 구독은 반복 결제의 부분집합인데 이 데이터로는 둘을 구별할 수 없다(고정 금액·월 주기라는 신호는 3개월치가 있어야 나온다).

**임계값:** 같은 가맹점 3회 이상, 또는 2회이면서 파일 기간이 30일 이상일 때 반복으로 본다. PG 적요는 제외한다(4.4).

### 4.11 Next.js App Router (결정 11)

서버가 필요하고(4.1), Harness를 태운다(결정 14). `harness/docs/ARCHITECTURE.md` 템플릿이 이미 `app/`(페이지 + API 라우트) + `components/` + `types/` + `lib/` + `services/` 구조를 전제로 쓰여 있어, 템플릿을 고치지 않고 그대로 채울 수 있다. Route Handler 하나로 업로드+파싱+LLM을 처리한다.

Harness의 `execute.py`가 매 step 프롬프트에 `CLAUDE.md` + `docs/*.md`를 통째로 주입하므로, 스택 선택이 문서에 적혀 있으면 모든 step이 그것을 지킨다. 스택을 문서 밖에서 정하면 가드레일이 작동하지 않는다.

### 4.12 PDF 내보내기 (결정 13)

저장하지 않으므로 새로고침하면 리포트가 사라진다. 파일로 남길 수단이 필요하다.

**브라우저 인쇄(`@media print`)로 구현한다.** 서버 렌더링 PDF는 저장 없는 정책에 비해 과한 장치다.

1차 문서의 결정 13은 "PDF/이미지"였으나 이미지 내보내기 수단을 정하지 않았다. 인쇄 하나로 좁힌다 — PDF로 저장하면 이미지 요구도 대체로 덮인다.

## 5. 산출물 명세

### 5.1 처리 파이프라인

```
업로드 (csv)
  └ 파싱          헤더 행 탐색 → 더미 컬럼 제거 → 날짜/금액 정규화
  └ 취소 쌍 탐지   적요+절대금액 키, 1:1 그리디, 취소>결제 (시간 상한 없음)
  └ 소비 필터      체크카드결제 + 출금 (음수만)
  └ 분류          메모 → 규칙 → LLM → 미분류   (PG 적요는 메모에만 의존)
  └ 이벤트 묶음    메모 반복 키워드
  └ 집계          카테고리별·이벤트별·반복·집중도
  └ AI 요약       집계 결과만 LLM에 전달
  └ 응답          정규화 거래 배열 + 집계 (4.2)

[클라이언트] 사용자 입력(카테고리 / 소비 아님) → analyze.ts 재집계 → 리포트 갱신
```

취소 쌍 탐지가 소비 필터보다 앞선다. 취소 행은 양수라 소비 필터를 먼저 돌리면 사라진다.

### 5.2 11일 샘플 기준 회귀 픽스처

> **이 값들은 11일치 샘플(`fixtures/toss-sample.csv`) 전용 회귀 테스트 기댓값이다.** 권장 사용 기간(3~6개월, 4.10)의 리포트가 어떻게 보일지를 나타내지 않는다.
> **전 항목 실데이터 검산 완료.**

```
소비 총액     2,077,810원 / 23건   (카드+출금, 취소 2건 303,750원 제외)

취소 쌍       롯데시네마_티켓_토스페이_TOSS  36,000  (24초 간격)
              (주)그린카                  267,750  (42시간 간격)

반복 결제     쿠팡이츠 4회 102,300원        ← 이 파일에서 유일하게 임계값 통과
                (2회짜리 3건은 제외 — 4.10 임계값. 파일 기간이 11일뿐이라
                 2회는 반복의 증거가 못 된다:
                   쿠팡(쿠페이)      2회 817,990원
                   토스페이_TOSS     2회 121,930원   ← PG라 이중으로 제외
                   주식회사 놀유니버스 2회   4,000원   ← 항공권 예약 수수료)

이벤트        제주 여행 7건 782,430원 — 같은 파일 기간(11일) 소비의 37.7%
                └ 메모에 `제주` 포함        5건 778,430원
                └ 놀유니버스 수수료          2건   4,000원  ← 키워드로는 안 잡힌다 (2.5, 8.3)
              울진 여행 0건 0원 — 유일한 울진 지출 그린카가 취소 쌍이라 전부 제외됐다.
                따라서 이벤트 이름은 "제주 여행"이다

집중도        상위 3건이 전체의 60.8%
                쿠팡(쿠페이)                          769,900원  ← 품목 불명, 사용자 입력 대상 (4.5)
                제주>김포 항공권 2인 (대한항공)          275,000원  ← 여행 이벤트와 중복
                제주 2일 숙박 (엔에이치엔케이씨피 ㈜)     218,500원  ← 여행 이벤트와 중복, PG 표시명 치환

사용자 입력 필요  출금 2건 (박상은서울주민 6,000 / 여행비 200,000)
                + 고액 미상세 1건 (쿠팡(쿠페이) 769,900)
```

**이벤트 합계 782,430원이 `여행비 입금` 행 금액과 정확히 일치하는 것은 우연이 아니다.** 사용자가 여행 비용을 정산해 그 금액만큼 입금한 것이다. 설계 검토 중 "입금액을 실수로 옮겨 적은 것 아니냐"는 의심이 있었으나, 실데이터 검산 결과 지출 7건의 합이 실제로 782,430원이었다.

**표시명 규칙:** 메모가 있으면 표시명을 메모 기반으로 쓰고 원본 적요를 괄호로 부기한다. PG 적요를 그대로 노출하면 사용자가 읽을 수 없는 발견이 된다(2.4).

**중복 계상:** 집중도 상위 3건 중 2건이 여행 이벤트에 이미 포함돼 있다. 발견 항목끼리 같은 돈을 공유한다는 사실을 리포트에 명시한다. 안 그러면 37.7% + 60.8%를 더해 읽는다.

### 5.3 리포트 섹션

0. **업로드 화면** — 변환 안내 3단계 (2.8)
   1. 토스뱅크에서 받은 `.xlsx`를 엑셀·넘버스·구글시트로 연다
   2. 비밀번호를 입력한다
   3. `CSV`로 내보낸 뒤 그 파일을 올린다
1. **요약** — 기간, 소비 총액, 건수, 제외된 취소 건, **2인 공동 계좌 합계 고지** (4.8)
2. **발견** ← 주인공. 반복 결제, 이벤트 묶음, 집중도, 미분류 비중, 항목 간 중복 고지
3. **카테고리별 지출** — 근거로 까는 회고 정보
4. **이벤트 묶음** — 카테고리와 별개 축
5. **AI 요약** — 집계 결과만 받아 문장 몇 줄
6. **기간 한계 고지** — 조회기간이 짧으면 반복 결제 탐지 불가를 명시
7. **데이터 처리 고지** — 업로드 파일은 저장하지 않으며, **분류되지 않은 가맹점명은 OpenAI로 전송**된다. 금액·계좌·성명은 전송하지 않는다 (4.1, 4.4, 8.1)

> **위 목록은 "무엇이 들어가야 하는가"이지 "어떤 순서의 섹션인가"가 아니다.** 화면 배치의 정본은 `UI_GUIDE.md`의 "화면 구성" 절이다. 거기서 **이벤트(4번)는 발견 섹션 안의 2번 카드**이고, **기간 한계(6번)와 데이터 처리 고지(7번)는 푸터 노트**에 들어간다. 7개 항목은 전부 배치되지만 7개의 독립 섹션이 되지는 않는다.

## 6. 프로젝트 구조

`harness` 템플릿 구조를 그대로 따르고, 플레이스홀더만 이 프로젝트 값으로 채운다.

```
spend-report/
├── CLAUDE.md              # harness/CLAUDE.md 템플릿을 채운 것 — 스택·CRITICAL 규칙
├── .gitignore
├── .claude/
│   ├── settings.json      # Stop 훅(lint·build·test), 위험 명령 차단
│   └── commands/
│       ├── harness.md     # step 설계 워크플로우
│       └── review.md      # 변경사항 리뷰 체크리스트
├── docs/                  # ← execute.py가 매 step 프롬프트에 통째로 주입
│   ├── DESIGN.md          ← 이 문서
│   ├── PRD.md
│   ├── ARCHITECTURE.md
│   ├── ADR.md
│   └── UI_GUIDE.md
├── fixtures/              # 로컬 전용. 커밋하지 않는다 (7.1)
├── phases/
│   ├── index.json         # phase 목록 + status
│   └── 0-initial-release/
│       ├── index.json     # steps 목록 + status
│       └── step0.md ~ stepN.md
├── scripts/execute.py     # harness/scripts/execute.py 복사
└── src/
    ├── app/
    │   ├── page.tsx               # 업로드 + 리포트
    │   └── api/analyze/route.ts
    ├── components/                # UI
    ├── types/                     # 거래·집계 타입
    ├── lib/                       # 순수 로직 — TDD 대상. 서버·클라이언트 공유
    │   ├── parse.ts               # csv → 거래 배열
    │   ├── cancel.ts              # 취소 쌍 탐지
    │   ├── categorize.ts          # 메모 → 규칙 → 미분류, PG 사전
    │   ├── events.ts              # 메모 키워드 이벤트 묶음
    │   └── analyze.ts             # 집계·발견 산출 (서버·클라이언트 양쪽에서 호출)
    └── services/openai.ts         # LLM 분류 + 요약
```

`src/` 하위는 `harness/docs/ARCHITECTURE.md` 템플릿의 디렉토리 구조(`app` / `components` / `types` / `lib` / `services`)를 그대로 따른다. `lib/`를 5개 모듈로 쪼갠 것만 이 프로젝트 고유다 — 5.1 파이프라인 단계와 1:1로 대응시켜 TDD 단위를 명확히 하기 위해서다.

### harness에서 가져오는 것

| 원본 | 처리 |
|---|---|
| `harness/scripts/execute.py` | 그대로 복사. 수정하지 않는다 |
| `harness/.claude/commands/*.md` | 그대로 복사 |
| `harness/.claude/settings.json` | 그대로 복사 |
| `harness/.gitignore` | 복사 후 `fixtures/` 추가 (7.1) |
| `harness/CLAUDE.md` | 템플릿. `{플레이스홀더}`를 이 프로젝트 값으로 채운다 |
| `harness/docs/{PRD,ARCHITECTURE,ADR,UI_GUIDE}.md` | 템플릿. 각각 채운다 |

원본을 고쳐야 하는 일이 생기면 그것 자체가 harness의 일반화 실패 신호다. 무엇을 왜 고쳤는지 기록한다(8.5).

### Harness 실행 구조

```
phases/index.json                     phase 목록 + status
phases/<phase>/index.json             steps + status + summary
phases/<phase>/stepN.md               step 지시문
scripts/execute.py <phase> [--push]   순차 실행
```

`execute.py`가 자동으로 하는 일:

- **가드레일 주입** — `CLAUDE.md`와 `docs/*.md` **전체**를 매 step 프롬프트에 넣는다. 이 문서(DESIGN.md)도 포함되므로, 설계 근거가 모든 step에 따라다닌다
- **컨텍스트 누적** — 완료된 step의 `summary`를 다음 step에 전달
- **자가 교정** — 실패 시 최대 3회 재시도. 직전 에러 메시지를 프롬프트에 피드백
- **2단계 커밋** — 코드 변경(`feat`)과 phase 메타데이터(`chore`)를 분리
- **브랜치** — `feat-<phase>` 생성/checkout

> **주의:** `execute.py`의 `ROOT`는 `scripts/`의 부모, 즉 `spend-report/`다. 하지만 git 저장소는 모노레포 루트(`ai-feature-lab`)이므로 `git add -A`가 **저장소 전체**를 대상으로 한다. spend-report 작업 중에는 다른 프로젝트 폴더에 미커밋 변경을 두지 않는다.

### 테스트 규율

**TDD 대상은 `src/lib/`만.** 파싱·취소 탐지·분류·집계가 조용히 틀리면 리포트 전체가 틀린다. UI 컴포넌트와 페이지에는 테스트를 요구하지 않는다.

검증은 **각 step 파일의 Acceptance Criteria**가 강제한다. 모든 step이 `npm run lint && npm run build && npm run test`를 AC로 갖고, 실패 시 `execute.py`가 에러 메시지를 프롬프트에 넣어 최대 3회 재시도한다.

> `.claude/settings.json`의 Stop 훅도 같은 커맨드를 돌리지만 **그것은 Claude Code 세션에만 걸린다.** `execute.py`의 러너는 `codex exec`이므로(6절 "Harness 실행 구조") harness 실행 중에는 이 훅이 발동하지 않는다. 안전망은 훅이 아니라 step AC다.

## 7. 검증 계획

### 7.1 픽스처 정책

**원본 CSV를 `fixtures/`에 로컬 보관하고 커밋하지 않는다.**

- 파일에 실명·계좌번호·실제 소비내역이 들어 있고 이 저장소는 공개 이력을 갖는다. 한 번 커밋되면 영구 기록이다
- `.gitignore`에 `fixtures/`를 넣는다
- 경로는 `fixtures/toss-sample.csv`로 고정한다. 테스트는 이 경로만 본다
- **대가: CI에서 이 테스트들이 돌지 않는다.** 완화책으로 픽스처가 없으면 해당 테스트를 skip하고, 기댓값은 5.2에 상수로 남겨 다른 환경에서도 재현 가능하게 한다

> **배치 완료.** `fixtures/toss-sample.csv`가 있고 `.gitignore`가 적용된 것을 확인했다. 이 파일은 한때 `docs/` 아래에 있었고 그 위치는 gitignore되지 않았다 — 커밋 직전이었다.

### 7.2 검증 항목

1. **단위 테스트** (`npm run test`) — `fixtures/toss-sample.csv` 기준. 파일이 없으면 skip한다
   - 헤더가 9번째 줄에서 발견되는가
   - 더미 첫 컬럼이 무시되는가
   - 취소 쌍 2건이 **모두** 잡히는가 (24초 / 42시간)
   - 취소 행이 결제보다 **앞선** 경우 짝지어지지 않는가
   - 같은 키의 결제가 여러 건일 때 **1건만** 소진되는가
   - 소비 총액이 `2,077,810원 / 23건`인가
   - `거래 유형`을 카테고리로 오인하지 않는가
   - 메모가 적요보다 우선 적용되는가 (엔에이치엔케이씨피 → 숙박)
   - PG 적요가 반복 결제 집계에서 빠지는가
   - 반복 결제로 `쿠팡이츠 4회 102,300원` **1건만** 나오는가 (2회짜리 3건은 임계값 미달 — 4.10)
   - 이벤트가 `제주 여행 7건 782,430원`인가. **키워드 매칭만 구현하면 5건 778,430원이 나와 실패한다** (8.3)
   - 울진 이벤트가 0건이라 리포트에 나타나지 않는가
2. **엔드투엔드** — `npm run dev` → CSV 업로드 → 리포트 → 출금 2건과 고액 미상세 1건이 입력 대상으로 뜨고, 카테고리 지정·`소비 아님` 선택이 **재업로드 없이** 총액에 반영되는가 (4.2 재집계 경로) → PDF 인쇄 미리보기
3. **LLM 미가용** — API 키 없이도 규칙 분류까지 동작하고 LLM 단계만 건너뛰는가
4. **암호화 xlsx 업로드** — 사용자가 실수로 원본 `.xlsx`를 올렸을 때, 파싱 실패가 아니라 **변환 안내 메시지**가 뜨는가 (2.8, 5.3)
5. **Harness** — `python3 scripts/execute.py 0-initial-release` (인자는 경로가 아니라 `phases/` 하위 디렉토리 **이름**이다)

## 8. 검토자에게 — 의심스러운 지점

이 설계에서 가장 공격받을 만한 곳을 스스로 꼽으면 아래다.

### 8.1 외부 전송이 저장보다 큰 노출면이다 ★가장 약한 고리

1차 문서는 "원본 전체 전송"과 헤더의 실명을 걱정했다. 방향이 틀렸다. 실명은 파싱 직후 버리면 끝이고 사람별 리포트도 만들지 않는다(4.8). **진짜 노출 경로는 OpenAI다.**

4.4가 미분류 적요를 외부 API로 보낸다. 그런데 이 컬럼에 든 것은:

```
탐앤탐스삼모타워신림역점       ← 건물명 + 역명
씨제이올리브영(주)신림중앙점    ← 지점명
신주옥미 신림역점             ← 지점명
(주)이마트 구로점             ← 지점명
```

**지점명은 실명보다 강한 식별자다.** 위 목록만으로 사용자의 생활 반경(신림)이 특정된다. 실명은 이름 하나지만 지점명 목록은 행동 패턴이다.

현재 완화책:
- 금액은 보내지 않는다 (4.4)
- 성명·계좌번호는 파싱 단계에서 버린다
- 출금 건(`박상은서울주민` 등 제3자 실명 포함)은 사용자가 직접 지정하므로 LLM에 가지 않는다 (4.5)
- 5.3-7에 사용자 고지 섹션을 둔다

**남은 질문:** 지점명을 잘라내고(`씨제이올리브영(주)신림중앙점` → `올리브영`) 보내는 게 맞지 않나. 브랜드명만으로도 분류는 되고 위치 정보는 사라진다. 다만 소상공인(`막불감동`, `영광과일`)은 잘라낼 접미가 없어 그대로 나간다 — 이쪽이 오히려 사전으로 못 잡아 LLM에 꼭 보내야 하는 건들이다. **이 처리가 충분한지 검토가 필요하다.**

CSV 전용 결정으로 파일 비밀번호 전송 리스크는 사라졌다(2.8).

### 8.2 메모 의존의 편향

메모 기반 분류는 이 샘플에서 잘 동작하지만, 샘플의 메모 13건 중 11건이 여행 정산이다. **메모를 전혀 안 쓰는 사용자**에게는 PG 건이 전부 미분류로 떨어진다. 그 경우 미분류 비중이 얼마나 커지는지 추정하지 않았다.

이 샘플만 봐도 PG 3건 340,430원 = 소비의 16%다. 메모가 없었다면 그대로 미분류다.

### 8.3 분류·묶음 알고리즘이 둘 다 미정

**(a) 이벤트 키워드 추출.** "메모의 반복 키워드로 묶는다"고 했지만 구체적 알고리즘이 없다. `제주`·`울진`은 사람 눈에 명백하지만 자동 추출 규칙은 정하지 않았다. LLM에 맡길지, n-gram 빈도로 뽑을지 미정이다.

이 선택을 가르는 실증 사례가 샘플에 있다:

```
"제주도 2일 숙박비"   ← 정상
"제주고 1일 숙박비"   ← 사용자 오타
"제주 왕복항공권/..."  ← 슬래시 구분
```

`제주`를 **부분문자열**로 매칭하면 셋 다 잡힌다. **토큰/형태소 단위**로 자르면 `제주고`가 빠져 50,630원이 이벤트에서 누락된다. 실사용 메모는 오타와 임의 구분자를 포함한다는 증거다.

**그리고 부분문자열 매칭으로도 부족하다.** 실데이터 검산 결과, `제주` 키워드로 잡히는 건 5건 778,430원뿐이다. 정답인 7건 782,430원과 4,000원 차이가 나며, 그 차이는 놀유니버스 예약 수수료 2건이다 — 메모가 `"항공권예약 대행수수료"`라 지명이 없다(2.5).

```
키워드 매칭만        5건 778,430원   ← 알고리즘이 실제로 내놓는 값
정답                7건 782,430원
차이                2건   4,000원   ← 항공권 결제와 9초/11초 간격
```

금액으로는 0.5%라 사소해 보이지만, **"부수 수수료는 메모에 지명이 없다"는 것은 일반 패턴**이다(예약 수수료, 환전 수수료, 해외 결제 수수료). 시간 근접성(같은 이벤트의 거래는 초~분 단위로 붙는다)을 보조 신호로 넣을지, LLM에 맡길지 결정해야 한다. **키워드 단독으로는 안 된다는 것만 확실하다.**

**(b) 메모 → 카테고리 매핑.** 2.5의 `"제주도 2일 숙박비" → 숙박` 화살표가 어떤 로직인지 문서에 없다. 메모도 자연어라 키워드 규칙(`숙박비`→숙박, `렌트`→교통) 또는 LLM이 필요하다. 이게 없으면 분류 파이프라인의 1순위 단계가 아무 일도 못 한다. 1차 문서는 (a)만 자백하고 (b)를 놓쳤다.

### 8.4 단일 샘플 기반 설계 — 그리고 그 대가를 이미 치렀다

포맷 사양 전체가 **토스뱅크 파일 하나**에서 나왔다. 계좌 종류나 조회기간에 따라 안내행 수나 컬럼이 달라질 가능성을 확인하지 못했다. 헤더 탐색을 유연하게 짜서 완화했지만 검증되지 않았다.

**1차 문서는 이 리스크를 "안내행 수가 다를 수 있다" 수준으로 과소평가했다.** 실제로 터진 것은 포맷 변주가 아니라 **접근권**이었다 — 원본 파일이 암호로 잠겨 있어서 아예 열 수 없었고(2.8), 그 결과 결정 3과 검증 항목 하나가 통째로 무효가 됐다. 파일 하나를 CSV로 변환해서 본 것과 원본 파일을 다뤄 본 것은 다르다.

### 8.5 Harness 템플릿 적합성 — 1차 결과

이 프로젝트의 부차 목적은 harness가 재사용 가능한 프레임워크인지 검증하는 것이다(1절). 구조를 세우면서 나온 1차 결과를 기록한다.

**고치지 않고 그대로 쓴 것:**

| 대상 | 결과 |
|---|---|
| `scripts/execute.py` | 무수정. `ROOT`가 `scripts/`의 부모라 폴더만 옮기면 그대로 돈다 |
| `.claude/commands/*.md`, `.claude/settings.json` | 무수정 |
| `docs/ARCHITECTURE.md` 구조 | 무수정. `app`/`components`/`types`/`lib`/`services`가 이 프로젝트에 그대로 맞았다 |
| `docs/PRD.md`, `docs/ADR.md` 구조 | 무수정. ADR은 슬롯이 3개뿐이지만 늘리면 그만이다 |

**값만 바꾼 것 (템플릿이 의도한 사용법):**

- `docs/UI_GUIDE.md` — 템플릿 예시는 다크 대시보드(`#0a0a0a`/`#141414`)인데 이 프로젝트는 **인쇄 산출물**이라 밝은 배경으로 뒤집었다. 다만 **구조(원칙 → 안티패턴 → 색상 → 컴포넌트 → 레이아웃 → 타이포 → 애니메이션 → 아이콘)는 그대로 살았다.** 안티패턴 표는 값이 아니라 규칙이라 무수정으로 유효했다. 템플릿이 제 역할을 한 사례다

**템플릿에 없어서 추가한 것:**

- `CLAUDE.md`에 Harness 실행 절 — 템플릿에는 없다. 프로젝트마다 phase 이름이 다르므로 있어야 한다
- `.gitignore`에 `fixtures/` — 프로젝트 고유

**실제로 드러난 harness의 약점 2가지:**

1. **모노레포에서 git 경계가 어긋난다.** `execute.py`의 `ROOT`는 `spend-report/`인데 git 저장소 루트는 `ai-feature-lab/`이다. `git add -A`가 저장소 전체를 대상으로 하므로, spend-report step을 돌리는 동안 다른 프로젝트의 미커밋 변경이 함께 커밋된다. 지금은 "실행 전 확인"으로 회피했지만 `execute.py`가 phase 디렉토리 기준으로 `git add`를 제한하는 게 맞다
2. **가드레일 주입량이 문서 크기에 비례한다.** `_load_guardrails()`가 `docs/*.md`를 **전부** 넣는다:

```
CLAUDE.md              1,733자
docs/ADR.md            2,973자
docs/ARCHITECTURE.md   1,985자
docs/PRD.md            1,410자
docs/UI_GUIDE.md       3,265자
docs/DESIGN.md        24,832자   ← 전체의 69%
─────────────────────────────
합계                  36,198자   (step 1회 호출당)
```

  step 12개 × 최대 재시도 3회면 이 양이 최대 36번 반복된다. DESIGN.md가 혼자 69%를 차지하는데, 대부분은 **설계 근거**라 매 step에 필요하지 않다. 선택적 주입(step별로 필요한 문서만 지정) 또는 문서 분할이 필요한 시점이 온다.

phase를 실제로 완주한 뒤 이 절을 갱신한다.

### 8.6 취소 매칭이 못 잡는 것

4.6의 알고리즘도 아래는 놓친다. 전부 샘플에 사례가 없어 검증 불가다.

- **부분 취소** — 절대금액이 다르면 매칭되지 않는다
- **적요 변형** — 취소 행 적요에 `취소` 접미가 붙는 은행이 흔하다. 샘플에서는 결제·취소 적요가 동일했지만 그게 토스뱅크의 규칙인지 우연인지 모른다
- **오탐** — 같은 가맹점에서 같은 금액을 결제하고 별개로 환불받은 경우를 취소 쌍으로 본다. 확률은 낮지만 상한 없는 매칭이라 기간이 길수록 커진다

### 8.7 (해소됨) 5.2 기댓값 검산 완료

1차 검토에서 5.2의 이벤트 기댓값 `782,430원 / 7건`이 의심받았다. 2.5에 열거된 여행 지출을 더하면 780,430원(6건)이었고, 782,430원은 `여행비 입금` 행 금액과 정확히 일치했기 때문이다 — 지출 합계가 아니라 입금액을 옮겨 적은 것 아니냐는 지적이었다.

**실데이터로 검산한 결과 기댓값이 맞았다.** 원인은 문서의 누락이었다: `주식회사 놀유니버스 -2,000`이 실제로는 **2건**인데 2.5가 1건만 열거했다. 7번째 건이 그것이다. 입금액과 일치하는 것도 우연이 아니라 사용자가 여행비를 정확히 정산한 결과다.

5.2의 모든 값(총액·건수·취소 쌍·반복 결제·집중도·이벤트)이 실데이터 검산을 통과했다. **다만 그 과정에서 8.3의 알고리즘 결함이 드러났다** — 기댓값은 맞지만 4.9에 적힌 키워드 매칭으로는 그 값이 나오지 않는다.

이 절은 기록으로 남긴다. 단일 샘플이라도 실제로 계산해 보기 전까지는 문서에 적힌 숫자를 믿을 수 없다는 사례다.
